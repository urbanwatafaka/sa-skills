# /tdd-draft [KEY] [автор]

Входы: `context.md`, `decisions.md`, `questions.md`, строки нужных ID из `impact-map.md` и `sources/BRD.md` (grep по ID, файлы целиком не читай), манифест шаблона (через `sa_draft.py plan`), блоки `shared/blocks/<блок>.md`. Выход: `draft/<секция>.md`, `draft/diagrams/*.puml`, `draft/api/*.yaml`, `draft/dto/*.json`, `draft.md`, `draft-publish.md`, отчёт самопроверки и пробелов.

`<база>` — базовая директория этого скила, `<плагин>` = `<база>/../..`. Все команды — из рабочей папки аналитика.

## Перед началом

Прочитай `<плагин>/shared/rules/ai-rules.md`, `<плагин>/shared/rules/writing-style.md`, `<плагин>/shared/rules/artifact-writing.md`, в `<плагин>/shared/schemas/artifacts.md` раздел «draft/ и draft.md» и `<плагин>/shared/blocks/diagrams.md`.

Файлы черновика пиши только по абсолютному пути: `<tasks_dir>/<KEY>/draft/<секция>.md`, `<tasks_dir>/<KEY>/draft/diagrams/<файл>.puml`, `<tasks_dir>/<KEY>/draft/api/<сервис>.yaml`, `<tasks_dir>/<KEY>/draft/dto/<ИмяDTO>.json`.

## Шаги

1. **Папка задачи.** `python3 <плагин>/scripts/sa_paths.py` — возьми `tasks_dir`, `repos_root` и `services` (для сверки с кодом на шаге 5). Первый аргумент похож на ключ (`[A-Z][A-Z0-9]+-[0-9]+`) — `tasks/<KEY>`, остаток ввода — автор; иначе единственная задача в `tasks/`, при нескольких — спроси. `python3 <плагин>/scripts/sa_status.py tasks/<KEY>`: стадия должна быть `start`, `clarify`, `draft` или `check`, иначе скажи, какую стадию запустить сначала, и остановись. Есть «Устаревшие входы» — предупреди, что входы менялись после прошлой стадии.
2. **Пробелы до сборки.** `python3 <плагин>/scripts/sa_draft.py gaps tasks/<KEY>`. Если в строках «Открытые блокирующие вопросы» или «Нерешённый скоуп» не `нет` — перечисли их и спроси: продолжить с плейсхолдерами `⚠ Q-…` или сначала закрыть вопросы в `/tdd-clarify`. Аналитик уже сказал продолжать — не спрашивай. Пункты карты со скоупом `?` описывай с плейсхолдером вопроса из Комментария строки.
3. **План.** `python3 <плагин>/scripts/sa_draft.py plan tasks/<KEY>`. Если сообщает «шаблона <тип> нет» — скажи аналитику, что шаблон этого типа ещё не заведён, и остановись. В шапке плана `ВНИМАНИЕ: в state.json feature@1.0` — черновик собран по старому шаблону: скажи аналитику и пересобери все секции заново по `feature@2.0`. На каждую секцию: обязательность, блок, виды диаграмм, статус (`нет`, `нет — без содержания не создаётся`, `есть`, `правка человека — не перезаписывать`) и срез `R` / `IM` / `D` — только эти ID относятся к секции. Прочитай `context.md` и `decisions.md` один раз. Затем сверь эталоны по `<плагин>/shared/etalons.md`, раздел «Проверка перед сборкой»: только номер версии, при росте — только разница версий; что поменялось и какие блоки могли устареть — в итог. Сборка не останавливается.
4. **Секции** — по порядку плана, кроме `правка человека` (их не трогай):
   - в перегенерируемых секциях замени плейсхолдеры `⚠ Q-…` закрытых вопросов (answered/obsolete) по решениям из `decisions.md`;
   - решение по отвеченному вопросу вноси в естественное место секции (таблица, шаг процесса, пункт доработки) тем же тоном, что и остальной текст, — тогда вопрос уходит из «Открытых вопросов». Места в тексте нет — допиши вопросу в `questions.md` строку `Ответ в ТЗ: <ответ>`, и он останется в разделе с ответом. Ответ частичный — подтверждённое в текст, на месте остатка `⚠ Q-…`;
   - прочитай `<плагин>/shared/blocks/<блок>.md` из плана — структура, правила и чек-лист секции;
   - строки `R-xx` и `IM-xx` из среза — grep по ID в `sources/BRD.md` и `impact-map.md`;
   - запиши `<tasks_dir>/<KEY>/draft/<секция>.md`: первая строка — заголовок секции из плана (`# <название>`, у `04-kafka` — `## Топики Кафка`); каждое утверждение заканчивается трассировкой вида `‹R-01, IM-02, D-01›` (только ID из артефактов задачи);
   - неизвестное (нет в BRD, карте, решениях) не придумывай: ставь `⚠ Q-PO-xx` / `⚠ Q-SA-xx` с ID открытого вопроса, недостающее значение — `ХХХХХ ⚠ Q-…`; подходящего вопроса нет — запомни для шага 6;
   - перегенерируешь секцию, которая уже была, — номера пунктов верхнего уровня не сдвигай (на них ссылаются «п.N»), после правки сверь все «п.N»;
   - записал или поправил секцию — сразу `python3 <плагин>/scripts/sa_draft.py mark tasks/<KEY> <секция>`; без этого сборка сочтёт секцию правкой человека;
   - необязательная секция, для которой нечего описывать, **не создаётся**: никаких «Не применимо», «Изменения не требуются», «Без изменений». То же для подразделов внутри секции (нет UI — нет «Требований к UI», нет Front — нет `### Front`);
   - `09-release` — проверь оба условия регламента по уже написанным `01-brd` и `03-changes`, а не только по словам аналитика; при условии 2 закрой дублирующий вопрос по `blocks/release.md`;
   - диаграммы — только виды из плана и только если есть что показать: прочитай `<плагин>/skills/puml-<вид>/SKILL.md`, запиши `<tasks_dir>/<KEY>/draft/diagrams/<секция>-<вид>.puml`, проверь `python3 <плагин>/scripts/sa_puml.py check <путь к .puml>` и вставь в секцию отдельной строкой `@diagram diagrams/<секция>-<вид>.puml`;
   - REST-доработка сервиса — `<tasks_dir>/<KEY>/draft/api/<сервис>.yaml` по `blocks/changes.md` и строка `@openapi api/<сервис>.yaml` в «2. API» этого сервиса; DTO сообщений Kafka — `<tasks_dir>/<KEY>/draft/dto/<ИмяDTO>.json` и `{{DTO:<ИмяDTO>}}` в ячейке.
5. **Сверка с кодом — текста и диаграмм, одним проходом.** После секций и диаграмм: `python3 <плагин>/scripts/sa_review.py asis tasks/<KEY>` — утверждения о существующем по сервисам. Запусти субагента `sa-skills:source-reader` в режиме сверки — по одному на сервис, где есть что сверять, параллельно. Сервиса нет в `services` или группа `без сервиса` — не сверяй, упомяни в итоге. Передай субагенту путь `<repos_root>/<сервис>` и:
   - утверждения этого сервиса из вывода `asis`;
   - элементы диаграмм этого сервиса как утверждения `[существует]`: не красные вызовы `ГЛАГОЛ /путь` на стрелках, таблицы `схема.таблица`, события Kafka и порядок вызовов между ними; красные — только если ведут к строке карты `изм.`/`удал.` (метод или таблица уже есть, меняется поведение): сверяется только то, что они есть и так называются. Остальные красные шаги не передавай — их в коде нет.

   Субагент заново читает код и подтверждает формулировку, а не только то, что файл есть. Вердикт `опровергнуто` или `не найдено` — расхождение; его не переписывай молча: собери списком для итога и пометь затронутое место в тексте плейсхолдером `⚠ Q-SA-xx`, на диаграмме — текстовым `(?)` (вопрос — на шаге 6). Сборка не останавливается.
6. **Новые вопросы.** Собери весь список неизвестного без вопроса, разведи по `question-routing.md` и выдай ID: `python3 <плагин>/scripts/sa_ids.py next tasks/<KEY> Q-PO <N>` и отдельно `… Q-SA <N>` (N=0 — без вызова). Допиши вопросы в `questions.md` по `artifact-writing.md` (влияет на поведение для пользователя или контракт — `— *open, blocking*`) и поставь `⚠ <ID>` в секциях. Ответу нужно согласование бизнеса или архитектурного комитета — строка `Согласование: …` по `shared/schemas/artifacts.md`. Раздел «Открытые вопросы» отдельно не пиши — сборка делает его из `questions.md`.
7. **Сборка.** `python3 <плагин>/scripts/sa_draft.py assemble tasks/<KEY> "<автор>"`. Автор — из ввода; при первой сборке его нет — спроси один раз. При публикации этот автор не заменяется учётной записью Confluence. При повторной сборке автора не передавай: берётся из `draft.md`. `draft.md` и `draft-publish.md` руками не правь — правь секции и собирай заново.
8. **Проверка.** `python3 <плагин>/scripts/sa_validate.py tasks/<KEY>` — исправляй секции (после каждой правки — `sa_draft.py mark tasks/<KEY> <секция>`), собирай заново, пока не `OK`. Затем:
   - `python3 <плагин>/scripts/sa_state.py record tasks/<KEY> BRD impact-map context questions` — если `decisions.md` нет;
   - `python3 <плагин>/scripts/sa_state.py record tasks/<KEY> BRD impact-map context questions decisions` — если `decisions.md` есть;
   - `python3 <плагин>/scripts/sa_state.py set tasks/<KEY> stage draft`
9. **Самопроверка.** Пройди собранный `draft.md` по чек-листам всех блоков созданных секций, по `writing-style.md` и доменному чек-листу: у каждой истории понятен триггер; предусловия учитывают всех участников; happy path прописан до результата; есть ветки неуспешной валидации, недоступности смежной системы и повторов; для денег, начислений и налоговых режимов рассмотрены возвраты, отмены, сторно (или сказано, почему неприменимы); описано, что будет при отключении функциональности с уже накопленными данными; разработчик по каждому пункту «Доработок» поймёт ожидаемый результат без повторного выяснения; текст Front и уведомлений не противоречит Back. Отчёт — один нумерованный список находок со сквозной нумерацией: сначала структурные и логические (одно нарушение — один пункт, с секцией и краткой рекомендацией), затем `## Текст` — орфография, пунктуация, обрывочные предложения (нет находок — блока нет). Плейсхолдеры на открытые вопросы находками не считаются.
10. **Публикация** — только по подразделу «Публикация ТЗ» в `<плагин>/shared/access/adapters.md`: предпросмотр, явное «публикуй», явно названные пространство и родительская страница. После публикации — `python3 <плагин>/scripts/sa_state.py set tasks/<KEY> published <ссылка>` и `python3 <плагин>/scripts/sa_state.py set tasks/<KEY> published.version <версия>` (шаг 7 адаптера). Без любого из условий не публикуй — дай путь `<tasks_dir>/<KEY>/draft-publish.md`.
11. **Итог аналитику**, коротко:
    - отчёт самопроверки с шага 9;
    - эталоны с шага 3: что поменялось и какие блоки могли устареть, либо «версия не записана» / «недоступна», если так;
    - расхождения текста и диаграмм с кодом с шага 5, если есть;
    - вопросы, закрытые как дубль «Условий релиза», — по одной строке;
    - вывод `python3 <плагин>/scripts/sa_draft.py gaps tasks/<KEY>` как есть, в блоке кода;
    - новые вопросы — вывод `python3 <плагин>/scripts/sa_questions.py export tasks/<KEY> PO` и `… SA`, если вопросы заводились;
    - где страница или файл для вставки; если проверка диаграмм была «только структура» — что синтаксис PlantUML не проверен;
    - следующий шаг: `/tdd-check` (с `--code` — независимая сверка с кодом); после новых ответов на вопросы — `/tdd-clarify`, затем `/tdd-update`.

## Чего не делать

- Не перезаписывай секции со статусом `правка человека`.
- Не правь `draft.md` и `draft-publish.md` руками.
- Не выдумывай сервисы, методы, поля, тексты для пользователя, числа: нет источника — плейсхолдер и вопрос.
- Не описывай пункты карты «вне скоупа» и не расширяй скоуп.
- Не создавай пустые разделы и заглушки — необязательной секции без содержания нет.
- Не переноси в текст ТЗ ссылки `файл:строка`, имена классов и файлов.
- Не публикуй без предпросмотра, явного «публикуй» и названных пространства и родительской страницы.
