# puml-sequence

`<база>` — базовая директория этого скила, `<плагин>` = `<база>/../..`. Перед работой прочитай `<плагин>/shared/blocks/diagrams.md`.

## Когда применять

- Процесс, где важен порядок вызовов между пользователем, сервисами, БД и Kafka. Одна диаграмма — один процесс в `:::expand Процесс: <название>`.
- Только пользовательские сценарии, меняющие данные. Чтение списков и экранов и дубли того же сценария из БО не рисуются.

Не применять: структура системы — `puml-c2`; таблицы — `puml-er`.

## Каркас

```plantuml
@startuml
autonumber "<b>[000]"
actor "Мерчант" as merchant
participant "lkp-front" as front
participant "lkp-back" as back
participant "partners-dashboard" as pd
queue "Kafka" as kafka
database "БД lkp" as db

== Сохранение анкеты с промокодом ==
merchant -> front: Сохраняет анкету
activate merchant
activate front
front -> back: POST /api/questionnaires
activate back
back [#red]-> pd: <color:red>GET /internal/promocodes/{code}/owner</color>
activate pd
pd [#red]--> back: <color:red>200, ИНН владельца</color>
deactivate pd
note right of back: <color:red>ИНН владельца = ИНН анкеты — 422,</color>\n<color:red>анкета не сохраняется</color>
back -> db: lkp.questionnaires — сохранить анкету
activate db
db --> back: ok
deactivate db
back -> kafka: QuestionnaireSavedEvent
back --> front: 200
deactivate back
front --> merchant: Анкета сохранена
deactivate front

== Начисление вознаграждения ==
pd --> kafka: QuestionnaireSavedEvent
activate pd
pd -> pd: Рассчитать вознаграждение партнёру
pd --> merchant: Письмо об успешной регистрации
deactivate pd
deactivate merchant
@enduml
```

## Соглашения

- Всегда `autonumber "<b>[000]"`; номера шагов в «Описании шагов» — те же.
- Несколько кейсов — в одной схеме разделами `== Раздел ==`. Внутри разделов **без** `alt`/`loop`/`opt`/`par`/`break`/`group`: ветки и ошибки (`403`/`422`) — заметками `note`.
- Участники — сервисы из карты влияния, роли из BRD (как их видит пользователь: «Страница приглашения (новая, публичная, без входа в ЛК)»), БД по схеме (`БД ПФ1: ishop_4 + prodamus`), Kafka — `queue`. Монолит — одним участником, внутренние классы — только в тексте статьи.
- Порядок участников слева направо — по графу смежности: связанные пары рядом, общий ресурс (БД) — с края.
- Текст стрелки по-русски, до двух строк. Вызов — метод и путь (`POST /internal/users/find`), не пересказ. БД — таблица `схема.таблица` и действие по-русски, без SQL, JSON и полей.
- Инициирующая стрелка — сплошная, ответ — пунктир. Стрелки — только из активированных линий.
- Kafka: сервис пишет — `Svc -> kafka: Событие`; сервис читает — `Svc --> kafka: Событие`. Стрелок `kafka -> Svc` нет, запись и чтение — две независимые стрелки.
- Фоновый процесс — стрелкой сервиса в себя («Фоновая проверка … раз в час»), отдельного участника «Фоновая проверка» нет.
- Самострелка последним действием перед `deactivate` рисуется криво: изменение данных — стрелкой в БД, отправка письма — командой в Kafka.
- Нельзя `deactivate X` и сразу `activate X` без сообщения на линии `X` (на границе разделов падает в Confluence): держи линию активной через границу.
- Новое (нет в коде, влияние `новый`/`изм.`) — `A [#red]-> B: <color:red>Текст</color>`, на каждую строку после `\n` — свой тег. Порядок существующих шагов — по коду, новых — по контексту обсуждения; неясно — `Q-SA`.

## Чек-лист

- [ ] Есть `autonumber "<b>[000]"`, нет `alt`/`loop`/`opt`.
- [ ] Нет участников вне карты влияния и ролей BRD.
- [ ] На стрелках вызовов — реальные или спроектированные методы, не пересказ.
- [ ] Kafka только со стрелками от сервиса: запись сплошная, чтение пунктир.
- [ ] Красным только нереализованное, теги цвета валидны.
