# sa-flow

`<база>` — базовая директория этого скила, `<плагин>` = `<база>/../..`. Все команды — из рабочей папки аналитика.

Скил только выбирает стадию и передаёт ей ввод аналитика. Работу стадий — решения, вопросы, секции, ревью — делают сами стадии `/tdd-*` по своим `SKILL.md` (`<плагин>/skills/<стадия>/SKILL.md`).

## Когда срабатывает

- **Ключ задачи.** В сообщении ключ задачи (`PF2-4100`), и в `tasks/` есть такая папка, или аналитик говорит начать новую задачу с этим ключом.
- **Ответы на вопросы.** Строки вида `Q-PO-01: …`, `Q-SA-03: …`, или фразы «PO ответил», «ответы по задаче».
- **Вопросы о ходе работы.** «Что дальше», «где мы», «продолжаем», «статус».
- **Согласие.** Короткое согласие («да», «давай», «ок», «запускай») сразу после предложения этого скила.
- **Не срабатывает.** На вопросы не про задачу, на разбор кода без задачи, на явную команду `/tdd-…`: её выполняет сама стадия.

Строка `[sa-skills] <KEY> · стадия …` в контексте сообщения — подсказка плагина со статусом задачи; используй её, но перед предложением всё равно запусти статус (шаг ниже).

## Что предлагать

Перед каждым ответом: `python3 <плагин>/scripts/sa_paths.py` — `tasks_dir`; задача — по ключу, иначе единственная в `tasks/`, при нескольких — спроси. `python3 <плагин>/scripts/sa_status.py tasks/<KEY>` — возьми строку «Следующий шаг» и счётчики. По ним:

| Состояние задачи | Что сказать |
|---|---|
| Задачи ещё нет | «Начинаю <KEY> с карты влияния — пришлите ссылку на BRD (Jira или Confluence)» → `/tdd-impact` |
| BRD неполный | **Остановка** «Вопросы PO» |
| Карта готова, контекста нет (стадия `impact`) | **Остановка** «Формулировка для границ» → `/tdd-start` |
| Есть открытые блокирующие вопросы или нерешённый скоуп | **Остановка** «Вопросы PO» и/или «Вопросы аналитику» → `/tdd-clarify` |
| Вопросы закрыты, черновика нет | «Блокирующих вопросов нет. Дальше — сборка черновика. Запускаю?» → `/tdd-draft` |
| Черновик собран, ревью не было | «Дальше — ревью со сверкой с кодом. Запускаю?» → `/tdd-check --code` |
| Черновик менялся после ревью | «Черновик менялся — повторное ревью (без сверки с кодом). Запускаю?» → `/tdd-check` |
| В ревью есть открытые замечания | **Остановка** «Замечания ревью» |
| Есть принятые, не внесённые | «Вношу принятые замечания <RV-xx…> в черновик. Запускаю?» → `/tdd-update` |
| Замечаний нет, «Следующий шаг» — финальная сверка с кодом | «Замечаний нет. Перед завершением — финальная сверка с кодом. Запускаю?» → `/tdd-check --code` |
| Замечаний нет, «Следующий шаг» — завершить | «ТЗ готово. Отметить завершённым? Опубликовать в Confluence?» → `sa_state.py set tasks/<KEY> stage done`; публикация — только по явной просьбе (остановка «Публикация») |
| Стадия `done` | «Задача завершена»; что-то поменялось — новые вводные идут в `/tdd-clarify` |

Предлагай один шаг за раз. Ответ «да» — запусти его, в конце снова предложи следующий по этой таблице.

## Точки остановки

В точке остановки ничего не запускай сам. Скажи, что нужно, и жди ответа.

1. **Вопросы PO.** Блок для пересылки — вывод `python3 <плагин>/scripts/sa_questions.py export tasks/<KEY> PO` как есть, в блоке кода — и строка: «Перешлите PO. Когда ответит — вставьте ответы сюда». Пришли ответы — это вход для `/tdd-clarify` (или `/tdd-impact`, если BRD был неполный).
2. **Вопросы аналитику.** Список ID с одной строкой на вопрос (`sa_questions.py export tasks/<KEY> SA`): «Ответьте здесь или скажите, где посмотреть». Ответ — вход для `/tdd-clarify`.
3. **Формулировка для границ.** «Опишите, что делаем и в каких рамках: цель, релиз, PO, что в скоупе и что нет». Ответ — вход для `/tdd-start`.
4. **Замечания ревью.** Список открытых: ID, важность, где, одна строка проблемы. «Какие принять, какие отклонить? Можно «все принять» или «RV-03 отклонить, остальные принять»». Ответ — вход для `/tdd-update`.
5. **Автор при первой сборке.** «Кого указать автором ТЗ?» — один раз, перед сборкой черновика.
6. **Публикация.** Только по явной просьбе: «В какое пространство и под какую страницу?» Дальше — как в `/tdd-draft`: предпросмотр и «публикуй».

Ответ в точке остановки сам по себе — уже согласие запустить нужную стадию: «да» отдельно не спрашивай. Ответы PO пришли — сразу `/tdd-clarify`; решения по замечаниям — сразу `/tdd-update`.

## Ответ на предложение

- **Согласие** («да», «давай», «ок», «запускай», «го») — запусти предложенную стадию.
- **Отказ или «потом»** — ничего не запускай; скажи одной строкой, где задача остановилась, и что продолжить можно словами «что дальше».
- **Другая просьба** («сначала поправь п.3», «добавь в решения…») — выполни просьбу через подходящую стадию (`/tdd-clarify` для решений, `/tdd-update` для правок черновика); предложенный шаг предложи снова после.
- **Новые вводные** вместо ответа (поменялось требование, новые ответы PO) — это вход для `/tdd-clarify`; после него — заново по разделу «Что предлагать».
- **Не понял ответ** — переспроси одной фразой, не угадывай.
- **Предложение не помнится** (новая сессия, перерыв) — не опирайся на память: снова посмотри статус и предложи шаг по разделу «Что предлагать».

## Чего не делать

- Не запускай стадию без согласия — кроме ответа в точке остановки.
- Не запускай две стадии подряд на одно «да»: одна стадия — одно согласие.
- Не делай работу стадии сам: не пиши решения, вопросы, секции черновика и `review.md` — это делают стадии своими командами и проверками.
- Не решай за аналитика: принять или отклонить замечание, скоуп, снять блокировку вопроса — только по его словам.
- Не публикуй и не меняй ничего в Jira и Confluence без явной просьбы.
- Не перебивай явную команду: аналитик написал `/tdd-…` — выполняется она, дирижёр не вмешивается и после неё только предлагает следующий шаг.
- Не запускай стадии QA (`/qa-*`): их запускают тестировщики.
- Не держи состояние в голове: перед каждым предложением — свежий статус задачи.
