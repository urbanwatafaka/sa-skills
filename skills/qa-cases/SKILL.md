# /qa-cases [KEY]

Входы: секции `draft/01-brd.md`, `draft/03-changes.md`, `draft/08-testing.md`, `decisions.md`, `context.md`, OpenAPI из `draft/api/`; при нужде — код сервисов через `source-reader`. Выход: `qa/units.md` (статусы), `qa/cases.md`, `qa/questions.md`, `qa/state.json`.

`<база>` — базовая директория этого скила, `<плагин>` = `<база>/../..`. Все команды — из рабочей папки.

## Перед началом

Прочитай `<плагин>/shared/rules/qa-cases.md` целиком, в `<плагин>/shared/rules/artifact-writing.md` разделы «Пути», «ID», «Вопросы», в `<плагин>/shared/schemas/artifacts.md` раздел «qa/». Пиши только в `<tasks_dir>/<KEY>/qa/` по абсолютному пути; файлы аналитика (`draft/`, `decisions.md`, `questions.md` и другие вне `qa/`) не меняй.

## Шаги

1. **Папка задачи.** `python3 <плагин>/scripts/sa_paths.py` — возьми `tasks_dir`, `repos_root`, `services`. Первый аргумент похож на ключ (`[A-Z][A-Z0-9]+-[0-9]+`) — `tasks/<KEY>`; иначе единственная задача в `tasks/`, при нескольких — спроси.
2. **Готовность.** `python3 <плагин>/scripts/sa_status.py tasks/<KEY>`: стадия `draft`, `check` или `done`, файл `draft.md` есть (`<tasks_dir>/<KEY>/draft.md`), нет открытых блокирующих вопросов PO и аналитику. Иначе скажи, что сделать (`/tdd-draft`, `/tdd-clarify`), и остановись. ТЗ без плагина (нет `draft/`) не поддерживается — так и скажи. `python3 <плагин>/scripts/sa_validate.py tasks/<KEY>`: ошибки вне `qa/` — покажи, предложи аналитику `/tdd-update` и остановись.
3. **Единицы покрытия.** `python3 <плагин>/scripts/sa_qa.py units tasks/<KEY>` — скрипт сам собирает проверяемые пункты ТЗ в `qa/units.md` и сохраняет ID при повторе. Прочитай `<tasks_dir>/<KEY>/qa/units.md`.
4. **ТЗ.** Прочитай `draft/01-brd.md`, `draft/03-changes.md`, `draft/08-testing.md`, `decisions.md`; в `context.md` — только границы скоупа. OpenAPI из `draft/api/` читай точечно (Grep по пути метода), когда нужны поля тела и ответа. Есть ли Front-доработки — по `### Front` в `03-changes.md`: нет — фронт-кейсов нет.
5. **Статусы единиц.** Правь в `units.md` только колонки Статус и Причина:
   - пункт ничего не проверяет («Тело — `multipart/form-data`», «MD5 не считать», ссылка на другой пункт) — `не поведение` с причиной;
   - проверку на стенде не устроить без помощи DevOps или разработки (недоступность смежного сервиса, повторы с паузами, выключенные уведомления хранилища, данные «до релиза») — `нужно решение` с причиной; кейс не пиши;
   - пункт про функционал, который не используется (решение в `decisions.md` или граница в `context.md`, например анкета мерчанта), — `не тестируется` с причиной «функционал не используется (D-xx)»; кейс не пиши;
   - статусы, поставленные человеком, не трогай; иначе `не тестируется` ставит только человек.
6. **Факты из кода.** Собери, чего нет в ТЗ, но нужно новичку: путь до экрана, названия меню, вкладок, полей и кнопок, поля тела существующих методов, таблицы и записи, топики, ключи Redis. Сначала индекс `docs/` сервиса (`<repos_root>/<сервис>/docs/`, Grep). Остальное — субагент `sa-skills:source-reader`, по одному на сервис из `services`, параллельно: путь `<repos_root>/<сервис>` и вопросы этого сервиса строками `[справка] <вопрос>`. Факт из ответа идёт в кейс, а его источник — в «Источник» кейса через `;`: `code: <репо>/<путь>:<строка>` (из индекса — `docs: <репо>/docs/<файл>#<раздел>`). Сервиса нет в `services` (не задан `SA_REPOS_ROOT` или нет клона) — не выдумывай, переходи к шагу 7.
7. **Неизвестное.** Текст ошибки, код ответа, правило — нет ни в ТЗ, ни в решениях, ни в коде: в кейсе плейсхолдер `⚠ Q-QA-xx`, вопрос — в `<tasks_dir>/<KEY>/qa/questions.md` (заголовок `# Вопросы QA <KEY>`, раздел `## Для аналитика`, формат `- **Q-QA-01** [<R/IM/D>] <вопрос> — *open*`). ID — одним вызовом `python3 <плагин>/scripts/sa_ids.py next tasks/<KEY> Q-QA <N>`.
8. **Кейсы.** По `qa-cases.md`: бэкенд — по методам «Описания изменений» Back и OpenAPI, включая ошибки и границы; фронт — по экранам «Что изменить» и «Требованиям к UI»; регресс — по «Сохраняемому поведению». Каждая единица со статусом пусто — хотя бы в одном «Покрывает». Один кейс может покрывать несколько единиц, если проверяет их одним прохождением. Кейс проверяет несколько случаев (ЛК и БО, два окна) — после каждого проверяющего шага подшаг `- Результат:` (раздел «Несколько случаев в одном кейсе» правил).
   - Первый запуск (`cases.md` нет) — пиши весь файл: `# Тест-кейсы <KEY>`, разделы `## Бэкенд`, `## Фронт`, `## Регресс`.
   - Повторный запуск — существующие кейсы не переписывай (это работа `/qa-update`); дописывай кейсы только для единиц без кейса; кейсу, добавленному руками без `TC-xx`, и второму кейсу с повторяющимся `TC-xx` (`precheck`: «ID повторяется») выдай новый ID, остальной текст не меняй.
   - ID новым кейсам — одним вызовом `python3 <плагин>/scripts/sa_ids.py next tasks/<KEY> TC <N>`.
9. **Отметка и проверка.** `python3 <плагин>/scripts/sa_qa.py mark tasks/<KEY> <TC-xx…>` — только кейсы, которые написал ты в этом запуске (первый запуск — `все`). Затем `python3 <плагин>/scripts/sa_qa.py precheck tasks/<KEY>`: исправляй свои кейсы, пока не останутся только строки «нужно решение» и плейсхолдеры открытых `Q-QA` (после правки — снова `mark` для исправленных). `python3 <плагин>/scripts/sa_validate.py tasks/<KEY>` — исправляй, пока в `qa/` нет ошибок.
10. **Итог**, коротко:
    - кейсов по видам (бэкенд, фронт, регресс), единиц всего и `не поведение`;
    - «нужно решение» — списком `U-xx — пункт — причина`: человек ставит `не тестируется` с причиной или просит написать кейс;
    - непокрытое, если осталось;
    - вопросы `Q-QA` аналитику — списком;
    - следующий шаг: `/qa-check`, затем прочитать `qa/cases.md` и сказать, что поправить (или править файл самому).

## Чего не делать

- Не выдумывай правила, тексты, коды ответов — только ТЗ, решения и код с источником `code:`.
- Не пиши кейсы для единиц `нужно решение`, `не тестируется`, `не поведение`, `удал.`.
- Не переписывай существующие кейсы и не восстанавливай удалённые руками.
- Не меняй колонки ID, Где и Пункт в `units.md` — их пишет скрипт.
- Не пиши о стендах, учётках и подготовке данных.
