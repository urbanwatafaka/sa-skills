# SA Skills: пайплайн системного аналитика — дизайн

Дата: 2026-10-15
Статус: на ревью команды

## 1. Цель и границы

Набор скилов для Claude Code, который проводит системного аналитика от BRD до проверенного черновика ТЗ:

1. Карта влияния на сервисы по BRD, документации и коду.
2. Старт контекста: цель, границы, тип ТЗ.
3. Уточнение BRD: вопросы, разделённые на PO и аналитика, журнал решений.
4. Черновик ТЗ по шаблону с диаграммами PlantUML.
5. Независимое ревью черновика.

Дополнительно в скоупе: атомарные скилы диаграмм `puml-*`, индексатор `/docs` по коду сервисов.

Главное нефункциональное требование: минимальный расход контекста LLM. Между вопросами и ответами могут пройти дни, поэтому каждая стадия должна запускаться в новой сессии только по файлам-артефактам, без пересказа истории.

Вне скоупа: автоматическая отправка вопросов PO (аналитик пересылает сам), автоматический коммит `/docs` в основные ветки сервисов, публикация ТЗ за пределы личного пространства.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Среда | Claude Code (CLI, IDE, desktop), упаковка — плагин |
| Доступ к Jira, Confluence, Git | Адаптер с выбором пользователя и фолбэком: MCP → CLI/REST → ручная вставка текста |
| Хранение артефактов | Локальная папка на задачу `tasks/<KEY>/` |
| Шаблоны ТЗ | В репозитории скилов, манифесты по типам (`feature`, `integration`), версионируются git |
| Источник знаний о системе | Индекс `/docs` в репозиториях сервисов, строится скилом `/sa-index-docs` |
| Диаграммы | PlantUML (C4-PlantUML для C2), макрос PlantUML в Confluence |
| Канал вопросов PO | Скил выдаёт готовый блок, аналитик пересылает; ответы вставляются в свободной форме |
| Нарезка скилов | Стадии — скилы; общие правила, блоки и шаблоны — справочные файлы плагина; диаграммы и индексатор — самостоятельные скилы |

### Почему такая нарезка

В Claude Code `description` каждого скила постоянно лежит в контексте, тело `SKILL.md` загружается при вызове, а `references` — только когда инструкция велит их прочитать. Поэтому:

- правила (`ai-rules`, `writing-style`, `block-*`) не делаются отдельными скилами: иначе это 20+ постоянных описаний и риск, что модель не вызовет нужную цепочку;
- стадия читает только справочники, нужные текущему шагу (например, `blocks/api.md` при сборке секции API);
- тяжёлое чтение (код, большие страницы) делается субагентами, которые возвращают выжимку с источниками;
- ревью делает отдельный субагент с чистым контекстом.

### Папка задачи

```
tasks/<KEY>/
├── state.json          # стадия, версии шаблона и плагина, хэши входов и секций
├── sources/            # выжимки источников: BRD.md, confluence-*.md, code-*.md
├── impact-map.md       # стадия 1
├── context.md          # стадия 2
├── questions.md        # открытые вопросы Q-PO-xx / Q-SA-xx
├── decisions.md        # журнал решений D-xx
├── draft/              # черновик по секциям: 01-context.md, 05-api.md …
│   └── diagrams/*.puml
├── draft.md            # собранная страница
└── review.md           # замечания ревьюера
```

Принципы:

- стадия читает только объявленные входы и пишет свои выходы; сырые источники сжимаются в `sources/` один раз;
- черновик хранится по секциям: обновление трогает только затронутые секции;
- сквозные ID: `R-xx` (пункты BRD), `IM-xx` (карта влияния), `Q-PO-xx` и `Q-SA-xx` (вопросы), `D-xx` (решения), `RV-xx` (замечания ревью).

## 4. Схемы артефактов

Формат: markdown с короткой шапкой (плоское подмножество YAML: `ключ: значение`, списки только в виде `[a, b]`), данные — в таблицах. Точные схемы и валидатор — `shared/schemas/artifacts.md` и `scripts/sa_validate.py`.

### 4.1 `sources/BRD.md`

```markdown
---
source: <url>
fetched: 2026-10-15
brd_complete: false
missing: [критерии успеха, роли]
---
| ID   | Требование                              | Тип    |
|------|-----------------------------------------|--------|
| R-01 | Запретить собственный промокод в анкете | функц. |
```

Полнота проверяется по `shared/rules/brd-checklist.md`. При `brd_complete: false` стадия 1 останавливается и выдаёт только `Q-PO`.

### 4.2 `impact-map.md`

```markdown
---
index_used: true
confidence_cap: высокая
---
| ID    | Объект                          | Вид    | Влияние | ← R  | Источник                 | Статус | Уверенность |
|-------|---------------------------------|--------|---------|------|--------------------------|--------|-------------|
| IM-01 | partners-dashboard: promocode/… | API    | новый   | R-01 | code: routes/api.php:142 | факт   | высокая     |
```

- Вид: процесс, сервис, модуль, API, Kafka, БД, роль, UI, конфиг.
- Влияние: новый, изм., удал., ?.
- Статус: факт (есть источник) или допущение.
- Допущение с низкой уверенностью автоматически становится `Q-SA`.

### 4.3 `questions.md`

```markdown
## Для PO
- **Q-PO-01** [R-01] Что делать с уже начисленными вознаграждениями саморефералам?
  Варианты: а) не пересчитывать; б) пересчитать; в) другое — *open*

## Для аналитика
- **Q-SA-01** [IM-03] Шлёт ли lkp-back событие в Kafka при сохранении анкеты?
  Где проверить: lkp-back/app/Events — *open*
```

Маршрутизация по `shared/rules/question-routing.md`:

- PO: бизнес-правила, приоритеты, тексты для пользователя, скоуп и MVP, поведение в бизнес-исключениях. Формулировки без имён сервисов, полей и API.
- Аналитик: всё, что проверяется по коду, документации или у разработки: контракты, БД, интеграции, нагрузка.
- Смешанный вопрос делится на два.
- Каждый вопрос ссылается на `R-xx` или `IM-xx`; где возможно, даются варианты ответа.
- Статусы: `open`, `answered`, `obsolete`; у вопроса может быть флаг `blocking`.

### 4.4 `decisions.md`

```markdown
| ID   | ← Q     | Решение                                   | Кто/где    | Дата       |
|------|---------|-------------------------------------------|------------|------------|
| D-01 | Q-PO-01 | Начисления саморефералам не пересчитываем | PO, чат ММ | 2026-09-09 |
```

### 4.5 `state.json`

```json
{
  "task": "LKP-4155",
  "stage": "clarify",
  "template": "feature@1.2",
  "plugin_version": "0.3.0",
  "access": {"jira": "mcp", "confluence": "cli", "git": "cli"},
  "inputs": {"BRD": "<sha1>", "impact-map": "<sha1>"},
  "sections": {"05-api": {"hash": "<sha1>", "edited_by_human": true}}
}
```

- `stage`: `impact`, `start`, `clarify`, `draft`, `check`, `done`.
- `template` появляется на стадии `start`.
- Счётчики открытых вопросов в состоянии не хранятся: `/tdd-status` считает их по `questions.md`, чтобы не было рассинхрона.
- Формат JSON выбран, чтобы скрипты плагина работали на стандартной библиотеке Python без установки зависимостей.

Каждая стадия при старте сверяет хэши входов и предупреждает, если вход изменился после построения зависимого артефакта.

## 5. Стадии

### 5.1 `/tdd-impact <ссылка>`

- Вход: ссылка на Jira или Confluence с BRD.
- Выход: `sources/BRD.md`, `impact-map.md`, `questions.md`, `state.json`.

Шаги:

1. Получить BRD через адаптер доступа, нормализовать в `R-xx`, проверить полноту. Если BRD неполный — записать `Q-PO` и остановиться.
2. По индексам `/docs` (`bctc.md` → сценарии и домены, `system_tech.md` → сервисы, API, Kafka, `DB.md` → таблицы) составить список кандидатов.
3. Проверить кандидатов субагентами `source-reader`, параллельно по одному на сервис. Субагент возвращает строки карты с источником `файл:строка`, без сырого кода.
4. Допущения с низкой уверенностью превратить в `Q-SA`.

Без индекса `/docs`: предупредить, искать напрямую по коду и Confluence, выставить `confidence_cap: средняя`.

### 5.2 `/tdd-start`

- Вход: формулировка аналитика (цель, границы, ограничения, релиз, PO) и `impact-map.md`.
- Выход: `context.md`.

Определяет тип шаблона и фиксирует его версию, записывает границы «в скоупе / вне скоупа» со ссылками на `IM-xx`, допущения, ссылки на артефакты аналитика. Противоречия между картой и границами становятся `Q-SA`. Исходники не перечитываются.

### 5.3 `/tdd-clarify [ответы | целевое поведение | ссылки]`

- Вход: `questions.md`, `decisions.md`, `context.md`, ввод аналитика.
- Выход: обновлённые `questions.md` и `decisions.md`.

Сопоставляет ответы с ID, ведёт журнал решений, ищет неоднозначности, противоречия и пропуски (в BRD, между BRD и решениями, между решениями). Итог: «закрыто N, новых M, блокирующих K» и готовый блок вопросов для PO. BRD целиком не перечитывается, только нужные строки `R-xx`. Стадия повторяется сколько угодно раз.

### 5.4 `/tdd-draft`

- Вход: `context.md`, `decisions.md`, `impact-map.md`, `sources/BRD.md`, манифест шаблона.
- Выход: `draft/*.md`, `draft/diagrams/*.puml`, `draft.md`, отчёт о пробелах.

Шаги:

1. Если есть блокирующие открытые вопросы — предупредить. Аналитик может продолжить; на месте неизвестного ставится плейсхолдер `⚠ Q-PO-03`.
2. Собрать ТЗ по секциям манифеста. Для каждой секции читать только её `blocks/<тип>.md` и релевантные `R`, `IM`, `D`.
3. Диаграммы — через скилы `puml-*`.
4. В утверждениях ставить ссылки трассировки `‹R-01, D-03›`; при публикации они сворачиваются.
5. Шапка: статус, автор, Jira, метка «ИИ-черновик».
6. Публикация в личное пространство Confluence через адаптер; без доступа — `draft.md` для ручной вставки.

Большие секции (API нескольких сервисов) могут собираться параллельными субагентами, каждый со своим срезом входов.

### 5.5 `/tdd-update`

Сравнивает `decisions.md` с последней сборкой, по ссылкам трассировки находит затронутые секции и перегенерирует только их. Секции с `edited_by_human: true` не перезаписываются — выдаётся предложение в виде diff. Если страница уже опубликована, она сначала подтягивается и сверяется с хэшами.

### 5.6 `/tdd-status`

Читает `state.json` и заголовки артефактов. Показывает стадию, открытые вопросы по адресатам, незаполненные секции, устаревшие входы.

## 6. Ревью: `/tdd-check [страница]`

Ревьюер — субагент `tdd-reviewer` с чистым контекстом. Получает только `draft.md` (или опубликованную страницу), `sources/BRD.md`, `impact-map.md`, `decisions.md`, манифест шаблона и чек-листы блоков.

Проходы:

1. Соответствие шаблону: обязательные секции, шапка, количество плейсхолдеров `⚠`. Проверяется детерминированно.
2. Покрытие BRD: для каждого `R-xx` есть US или критерий приёмки со ссылкой; матрица `R → секции`. Непокрытый `R` — критично.
3. Покрытие карты влияния: каждый `IM-xx` со статусом «новый» или «изм.» имеет секцию доработки или явно исключён в `context.md`.
4. Непротиворечивость: ТЗ против `decisions.md`, секция против секции (тексты ошибок, имена полей, коды ответов), ТЗ против BRD.
5. Проверяемость критериев приёмки: условие, действие, ожидаемый результат; без оценочных слов.
6. Полнота блоков по чек-листам `blocks/*.md`.
7. Сверка с кодом (флаг `--code`): выборочная проверка утверждений `[as is]` через `source-reader`. Утверждения `[to be]` не сверяются.

Выход — `review.md`:

```markdown
| ID    | Важность | Где            | Проблема                                  | ← Ссылка | Предложение         |
|-------|----------|----------------|-------------------------------------------|----------|---------------------|
| RV-01 | критично | 05-api         | R-04 не покрыт ни одним критерием приёмки | R-04     | добавить AC в US-02 |
```

и матрица покрытия `R → US/AC`.

Правила ревьюера: черновик не правит; у каждого замечания есть ссылка на ID и место; замечание без доказательства — уровень «совет». Важности: критично, важно, совет.

Цикл: аналитик принимает замечания → `/tdd-update` → повторный `/tdd-check` сравнивает с прошлым `review.md` и показывает закрытые и оставшиеся.

## 7. Диаграммы `puml-*`

Скилы: `puml-c2`, `puml-sequence`, `puml-activity`, `puml-er`, `puml-state`. Каждый вызывается из `/tdd-draft` или самостоятельно.

Содержимое каждого скила:

- когда применять и когда нет;
- обязательный каркас: `!include` C4-PlantUML для C2, общие skinparam, легенда;
- соглашения: имена участников из `impact-map`, на стрелках протокол и метод, нумерация шагов `[001]`, совпадающая с «Описанием шагов» в ТЗ;
- пометки изменений: стереотипы `<<new>>`, `<<changed>>`, `<<removed>>` с цветом;
- чек-лист самопроверки: нет участников вне `impact-map`, каждый шаг диаграммы есть в тексте, альтернативные ветки оформлены `alt`/`else`;
- синтаксическая проверка: `plantuml -syntax`, если доступен локально или через Docker; иначе только чек-лист с предупреждением.

## 8. Индексатор `/sa-index-docs [сервис|all]`

Строит и обновляет `/docs`:

- в каждом сервисе: `DB.md` (структура и пояснения), `tech.md` (API, Kafka, фоновые воркеры), `bctc.md` (домены и сценарии сервиса);
- глобально: `AGENTS.md` (где что лежит, правила актуализации), `system_tech.md` (сводная таблица API и Kafka, связи C2), `bctc.md` (сценарии → сервисы).

Правила:

- формат — таблицы фиксированной структуры, каждая строка со ссылкой `файл:строка`, чтобы `/tdd-impact` мог искать по ним grep-ом;
- инкрементальность: хранится commit SHA последней индексации, перечитываются только изменённые файлы;
- полный проход по сервису — субагентом, по одному на сервис;
- неоднозначности помечаются `?`, не угадываются;
- результат пишется только файлами в рабочую копию репозитория сервиса; ветки, коммиты и MR — на усмотрение разработчиков сервиса (у аналитиков может не быть доступа к MR).

### 8.1. Детализация (подпроект 5, 2026-10-16)

Стеки разнородны (.NET, Laravel с отдельным и встроенным фронтом, PHP 5.6 с шаблонизаторами, React), поэтому код читает LLM-субагент `docs-indexer`, а всё проверяемое делает stdlib-скрипт `scripts/sa_index.py`. Экстракторов под фреймворки нет; подсказки, где искать маршруты, БД и очереди по стекам, — в `shared/index/stack-hints.md`.

Команды `sa_index.py`:

| Команда | Что делает |
|---|---|
| `survey <repo>` | Карта без чтения кода: маркеры стека (`composer.json`, `*.csproj`, `package.json` …), папки маршрутов/миграций/конфигов очередей, число исходников (без `vendor/`, `node_modules/`, `bin/`, `obj/`, `.git/`), режим `full`/`incremental`, признак ручных правок `docs/`. |
| `changed <repo>` | Файлы, изменённые с `sha` из `docs/.sa-index.json` (коммиты и рабочая копия), и строки индекса со ссылками на них. Нет SHA или он недостижим → режим `full`. |
| `check <repo>` | Валидатор: фиксированные заголовки разделов и таблиц, нет пустых ячеек, `Код` = `путь:строка` (несколько — через `, `), файл существует, строка в пределах файла; ячейка (кроме `Код`), начинающаяся с `?`, — допустимая неоднозначность. |
| `stamp <repo>` | Пишет `docs/.sa-index.json`: `sha` HEAD, дата, версия плагина, sha256 каждого файла `docs/*.md`. Расхождение хэша при следующем запуске = ручная правка. |
| `aggregate` | Детерминированно собирает в `index_dir` глобальные `system_tech.md`, `bctc.md`, `AGENTS.md` из `docs/` всех сервисов. |

Схемы файлов сервиса (каждая строка таблицы — с колонкой `Код`; пустой раздел — одна строка `нет`, остальные ячейки `—`):

- `tech.md`: `## API` (Метод | Путь | Назначение | Код), `## Исходящие вызовы` (Куда | Метод или топик | Назначение | Код), `## Сообщения` (Брокер | Топик или очередь | Направление | Когда | Код; направление `публикует`/`читает`), `## Фоновые задачи` (Задача | Запуск | Что делает | Код).
- `DB.md`: `## Таблицы` (Таблица | Назначение | Ключевые поля | Код), `## Связи` (Из | В | Тип | Код). Без миграций `Код` указывает на модель или SQL в коде.
- `bctc.md`: одна таблица (Домен | Сценарий | Роль сервиса | Точки входа | Код).

Глобальные файлы: `system_tech.md` — таблица `Поставщик | Метод или топик | Потребители | Назначение` (формат, который уже читает `/tdd-impact`): поставщик — из `API` и сообщений `публикует`, потребители — из `Исходящих вызовов` (`Куда` = сервис, совпадение метода и пути; если `Куда` начинается с `?`, вызов привязывается по методу и пути к единственному другому сервису с таким API и помечается `? <сервис>`) и сообщений `читает` того же топика; плюс таблица связей C2 `Из | В | Через`. `bctc.md` — `Сценарий | Домен | Сервисы`, объединение по точному имени сценария. `AGENTS.md` — список сервисов с путями, `sha` и датой индексации, правила актуализации.

Поток: `sa_paths.py` → `survey` → субагент на сервис (при `all` — параллельно) → субагент сам пишет `docs/*.md` и правит до чистого `check` → `stamp` → после всех сервисов `aggregate`. Инкрементально субагент получает вывод `changed` и правит только строки, ссылающиеся на изменённые файлы, плюс новое в этих файлах; ручные правки остальных строк сохраняются. Полный проход по файлу с ручной правкой — только после согласия аналитика. Если `survey` насчитал больше 1500 исходников, вместо одного субагента запускаются три — по `tech.md`, `DB.md`, `bctc.md`.

## 9. Доступ к источникам

`shared/access/adapters.md` описывает для Jira, Confluence и Git порядок попыток:

1. MCP-сервер, если подключён;
2. CLI или REST с токеном из переменных окружения;
3. ручной режим: скил просит вставить текст или выгрузку и продолжает работу.

Выбор режима сохраняется в `state.json` задачи. Ошибка доступа не прерывает стадию, а переводит её на следующий режим с сообщением пользователю.

## 10. Обработка ошибок и остановки

| Ситуация | Поведение |
|---|---|
| BRD неполный | Стадия 1 пишет только `Q-PO` и останавливается |
| Нет индекса `/docs` | Поиск напрямую, `confidence_cap: средняя`, предупреждение |
| Вход изменился после построения артефакта | Предупреждение со списком устаревших артефактов, предложение перезапустить стадию |
| Блокирующие вопросы при `/tdd-draft` | Предупреждение; при продолжении — плейсхолдеры `⚠ Q-xx` |
| Ручная правка секции | `/tdd-update` предлагает diff, не перезаписывает |
| Нет PlantUML для проверки | Только чек-лист, предупреждение в отчёте о пробелах |

## 11. Тестирование

- Эталонные задачи: 2–3 реальных кейса команды (промокоды в анкете, сотрудники компании, платёжная интеграция) с ожидаемыми артефактами: список `R`, ключевые `IM`, маршрутизация `Q-PO`/`Q-SA`, обязательные секции.
- Валидатор схем артефактов (скрипт), используется и в eval, и самими стадиями.
- Прогон через `claude plugin eval` по каждой стадии отдельно:
  - структура артефактов;
  - в `Q-PO` нет технических терминов (имён сервисов, полей, методов);
  - покрытие эталонных `R` и `IM`;
  - ревьюер находит заранее подложенные дефекты в испорченном черновике.
- Фиксация расхода токенов по стадиям, чтобы регрессия стоимости была видна так же, как регрессия качества.
