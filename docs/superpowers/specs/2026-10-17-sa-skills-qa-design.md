# SA Skills: стадии QA — тест-кейсы из ТЗ — дизайн

Дата: 2026-10-17
Статус: на ревью
Заказчик и первый пользователь: аналитик (бывший QA), обкатка на себе, задача-образец PF2-3964.

## 1. Зачем

У QA больше всего времени уходит на чтение ТЗ и написание тест-кейсов. Поэтому кейсы часто не пишут вовсе и тестируют «по пониманию». ТЗ, собранное плагином, уже структурировано: истории с критериями приёмки, «Доработки» по сервисам с методами и полями, «Тестирование и регресс», журнал решений, трассировка `‹R-xx, IM-xx, D-xx›`. Стадии QA превращают такое ТЗ в ручные тест-кейсы, проверяют полноту и выгружают в Allure TestOps.

Критерий качества кейса (слова заказчика): **по кейсу может пройти новичок на проекте** — подробные и понятные шаги. Новичок — опытный тестировщик, который ещё не прошёл онбординг в команду: тестировать умеет, но не знает продукт, экраны, методы и данные.

## 2. Цели, не-цели, анти-цели

**Цели**

1. По готовому ТЗ задачи (`tasks/<KEY>/`) сгенерировать ручные тест-кейсы: бэкенд — всегда, когда в ТЗ есть Back-доработки; фронт — только когда в ТЗ есть Front-доработки.
2. Полное покрытие: каждое проверяемое утверждение ТЗ покрыто хотя бы одним кейсом, непокрытое показано списком.
3. Локальное ревью кейсов человеком: замечания словами (Claude правит) и ручные правки файла (плагин их не затирает).
4. Выгрузка в Allure TestOps после явного «загружай»: сейчас — CSV для ручного импорта, позже — напрямую (подключение настроят позже).
5. При изменении ТЗ — найти задетые кейсы по трассировке, показать изменения, обновить после «да».

**Не-цели**

- Тест-план (заказчик: не нужен).
- Автотесты (пока только ручные кейсы).
- Сведения о стендах, учётках, подготовке тестовых данных — их новичку выдают отдельным процессом.
- Отдельный плагин: это дополнение sa-skills.

**Анти-цели (провал, даже если «работает»)**

- Кейсы с расплывчатыми шагами или результатом: «проверить, что загрузка работает», «работает корректно», «отображается правильно».
- Выдуманные в кейсах правила, тексты, коды ответов, которых нет в ТЗ или решениях.
- Затёртые ручные правки QA.
- Правки QA в артефактах аналитика.

## 3. Ограничения

- Те же, что у плагина: Python ≥ 3.10 только стандартная библиотека, Windows, вывод UTF-8, артефакты — markdown, минимальный расход контекста, каждая стадия запускается в новой сессии только по файлам.
- Вход — только ТЗ, собранное плагином (стадия задачи `draft`, `check` или `done`). ТЗ без плагина не поддерживается.
- QA пишут **только** в `tasks/<KEY>/qa/`. Файлы аналитика (`draft/`, `decisions.md`, `questions.md` и т.д.) стадии QA не меняют.
- Задачи живут в общем git-репозитории (gibus `payform-2.0/QA/sa-tasks`, пока локально). Отдельная доработка — настраиваемый путь `SA_TASKS_DIR` (п.19 в `docs/feedback/2026-10-16-pf2-3964-run.md`); стадии QA должны брать `tasks_dir` только из `sa_paths.py`.
- Правила разработки — `CLAUDE.md` репозитория (тесты-контракты, фикстуры, версия).

## 4. Решения заказчика

| Вопрос | Решение |
|---|---|
| Что на выходе | Только тест-кейсы, без тест-плана |
| Виды кейсов | Бэкенд и фронт; фронт — только при Front-доработках в ТЗ |
| Обязательные поля | Название, короткое описание, предусловия, шаги, ожидаемый результат |
| Ожидаемый результат | Один, в конце кейса; если кейс проверяет несколько случаев — ещё подшаг «Результат:» после каждого проверяющего шага (уточнение заказчика 2026-10-18) |
| Бэкенд-шаг | «Вызвать метод `POST /путь`» без указания инструмента (Swagger/Postman), с готовым телом запроса |
| Проверки вне ответа | Можно: у QA есть доступ к БД, Kafka, Redis — кейс называет таблицу и запись, топик и сообщение, ключ |
| Предусловия | Только условие («мерчант с каналом продаж»), без стенда и учёток |
| Полнота | Покрыто всё проверяемое в ТЗ: критерии приёмки, пункты «Доработок» (включая ошибки и границы), пункты «Тестирование и регресс» |
| Ревью | Локально, один файл кейсов; и замечания словами, и ручные правки |
| Allure | Загрузка после ревью и явного «загружай»; подключение позже, до него — CSV |
| Изменение ТЗ | Найти задетые кейсы, показать, обновить после «да» (предложение Claude, заказчик не возражал) |
| Источник сведений для кейса | ТЗ и код сервисов: можно читать фронт и бэк (как при сборке ТЗ), сведения из кода помечаются источником `code:` |
| Проверки, которые на стенде без помощи не устроить | Кейс не пишется сам: плагин спрашивает человека, тот помечает единицу «не тестируется» с причиной или просит написать кейс |
| Где живёт | Новые стадии `/qa-*` в sa-skills |

## 5. Стадии

Названия рабочие.

### `/qa-cases [KEY]` — сгенерировать кейсы

1. Проверить готовность: стадия задачи `draft`/`check`/`done`, `draft.md` собран, нет блокирующих открытых вопросов. Иначе — сказать, что делать, и остановиться.
2. Прочитать (по ID, не целиком, как стадии ТЗ): секции `01-brd` (истории и критерии), `03-changes` (Front/Back по сервисам), `08-testing`, `decisions.md`, `context.md` (границы), OpenAPI из `draft/api/`.
   - Чего нет в ТЗ, но нужно новичку (путь до экрана, названия меню и кнопок, поля тела существующих методов, таблицы, топики, ключи Redis), — уточнить по коду через субагент `source-reader` (по сервису, параллельно) или индекс `docs/` от `/sa-index-docs`. Такие факты в кейсе помечаются в «Источнике» как `code: <репо>/<путь>:<строка>` и проверяются `/qa-check`. Для этого у QA должен быть задан `SA_REPOS_ROOT` с клонами сервисов.
3. Собрать **перечень проверяемого** — единицы покрытия (§6).
4. Сгенерировать кейсы в `qa/cases.md` (§7): бэкенд-кейсы по методам «Доработок» и OpenAPI; фронт-кейсы по экранам Front и «Требованиям к UI»; регрессионные — по «Сохраняемому поведению».
5. Неизвестное для кейса, чего нет ни в ТЗ, ни в коде (текст ошибки, код ответа, правило), — не выдумывать: плейсхолдер `⚠ Q-QA-xx` и вопрос аналитику в `qa/questions.md`.
6. Единицы, которые на стенде не устроить без помощи DevOps или разработки (недоступность смежного сервиса, повторы с паузами, выключенные уведомления хранилища, данные «до релиза»), — кейс не писать. Остальные кейсы сгенерировать, а такие единицы вывести списком «нужно решение»: человек ставит «не тестируется» с причиной или просит написать кейс. Список виден в матрице покрытия и в `/tdd-status`, пока решение не принято.
7. Запустить валидатор, записать хэши входов. Итог: число кейсов по видам, непокрытое, вопросы.

### `/qa-check [KEY]` — проверить кейсы

- Скрипт: покрытие (каждая единица §6 → хотя бы один кейс), обязательные поля, плейсхолдеры, запрещённые формулировки из словаря (§8).
- Субагент-ревьюер с чистым контекстом (новый агент `qa-reviewer` по образцу `tdd-reviewer`): читает ТЗ и `qa/cases.md`, ищет кейсы, которые новичок не пройдёт без уточнений, противоречия с ТЗ, пропущенные негативные ветки.
- Результат — `qa/review.md` с замечаниями `QV-xx` и матрицей покрытия; повторный запуск закрывает исправленное (как `/tdd-check`).

### Ревью человеком (без отдельной команды)

- Человек читает `qa/cases.md` и либо говорит, что поправить (Claude правит в рамках `/qa-update` или по прямой просьбе), либо правит файл сам.
- Ручная правка кейса отмечается так же, как правка секции ТЗ: хэш кейса в состоянии не совпал с записанным стадией → кейс «правка человека», стадии его не перезаписывают, а кладут предложение рядом.

### `/qa-export [KEY]` — выгрузить в Allure

- Предпросмотр: какие кейсы уйдут (новые, изменённые, неизменные).
- Без явного «загружай» — ничего не выгружать.
- Сейчас: файл `qa/allure-import.csv` для ручного импорта (§9).
- Позже (подключение к Allure TestOps): создание и обновление кейсов через API, сохранение соответствия `TC-xx` ↔ ID в Allure, обновление вместо дублей.

### `/qa-update [KEY]` — обновить после изменения ТЗ или по замечаниям

- По снимку строк `R-xx`/`IM-xx`/`D-xx` и секций ТЗ на момент генерации найти задетые кейсы (трассировка кейса, §7).
- Показать список: какой кейс, почему задет, что изменится.
- После «да» — перегенерировать задетые кейсы; кейсы с правкой человека — только предложением.
- Принятые замечания `qa/review.md` вносятся здесь же.
- Если кейсы уже были в Allure — отметить их к повторной выгрузке (`/qa-export`).

### `/tdd-status` — дополнить

Строки про QA: сколько кейсов (бэкенд/фронт/регресс), непокрытое, открытые `Q-QA`, правки человека, что выгружено и что изменилось после выгрузки.

## 6. Единицы покрытия

Из ТЗ берутся автоматически (по разметке, которую уже знает плагин):

| Откуда | Единица |
|---|---|
| `01-brd`, таблица User Stories | каждый пункт `•` в «Критериях приемки» |
| `01-brd`, «Требования к UI» | каждый пункт списка |
| `03-changes`, Back | каждый пункт и подпункт «Описания изменений», описывающий поведение или ошибку (код ответа, проверка, запись, событие) |
| `03-changes`, Front | каждый пункт «Что изменить» |
| `08-testing` | каждый пункт «Нового поведения» и «Сохраняемого поведения» |

Единица получает стабильный идентификатор `U-xx` (сквозной в задаче, не переиспользуется), чтобы матрица покрытия и `/qa-update` опирались на него.

*Решение Claude:* перечень единиц собирает **скрипт** — все пункты и подпункты перечисленных мест, детерминированно. Модель при генерации может пометить единицу «не поведение» (например, «Тело — `multipart/form-data`», «MD5 не считать») — такая пометка видна в матрице покрытия с причиной, и человек может её снять. Пометка «не тестируется» (поведение есть, но проверить нельзя) ставится только решением человека с причиной — по аналогии со «вне скоупа» в `context.md`.

## 7. Формат кейса

Один файл на задачу: `tasks/<KEY>/qa/cases.md`. Разделы «Бэкенд», «Фронт», «Регресс». Кейс — подраздел строгой структуры, чтобы скрипт мог разобрать его в CSV и проверить:

````markdown
### TC-03 Загрузка логотипа больше 5 МБ отклоняется

- **Вид:** бэкенд
- **Приоритет:** High
- **Покрывает:** U-07, U-21
- **Источник:** ‹R-01, IM-05, D-13›

**Описание:** Метод загрузки файла канала продаж не принимает файл больше 5 МБ.

**Предусловия:** Мерчант с каналом продаж; файл PNG размером 6 МБ.

**Шаги:**
1. Вызвать метод `POST /api/files` с файлом 6 МБ в поле `file`.

**Ожидаемый результат:** Ответ `400`; документ не создан — в `public.Document` нет новой записи.
````

- Тело запроса — fenced-блок `json` внутри шага.
- Фронт-кейс: шаги по интерфейсу, названия как на экране; тексты — в «ёлочках» дословно из ТЗ.
- `TC-xx` — сквозная нумерация в задаче, не переиспользуется (как прочие ID плагина).
- `Покрывает` — обязательная явная ссылка на единицы §6; по ней считается покрытие (*решение Claude:* метки ‹R/IM/D› общие для многих единиц, по ним покрытие не определить).
- `Источник` — трассировка на ID ТЗ; по ней `/qa-update` находит кейсы, задетые изменением строк ТЗ.
- *Решение Claude:* ручное удаление кейса — решение человека: стадии его не восстанавливают, а `/qa-check` показывает единицы, оставшиеся без кейса. Кейс, добавленный руками без `TC-xx`, получает ID при следующем запуске стадии; кейс без `Покрывает` — замечание `/qa-check`, не ошибка.
- Приоритет — `High`/`Medium`/`Low`. Правило по умолчанию (решение Claude, можно поменять): High — основной сценарий и ошибки из критериев приёмки; Medium — остальное новое поведение; Low — регресс.

Поля совпадают с форматом QA из `payform-2.0/QA/AI-GEN-TESTS` (`name`, `description`, `preconditions`, `steps`, `expected_result`, `priority`), чтобы кейсы потом можно было подать и в их конвейер автотестов.

## 8. Проверки качества

Скриптом:
- у кейса есть все обязательные поля и хотя бы один шаг;
- `Источник` непуст и ссылается на существующие ID;
- каждая единица покрытия покрыта или помечена «не тестируется» с причиной;
- нет плейсхолдеров `⚠ Q-QA-xx` на закрытые вопросы;
- словарь расплывчатых формулировок в шагах и результате: «корректно», «правильно», «успешно» без уточнения, «проверить, что работает», «и т.д.», «при необходимости»; ожидаемый результат бэкенд-кейса без кода ответа.

Ревьюером: пройдёт ли новичок без вопросов; противоречия с ТЗ; пропущенные негативные ветки (ошибки, недоступность смежного сервиса, повторы, нет прав, пустые значения).

## 9. Выгрузка в Allure (CSV)

Эталон — генератор QA в репозитории gibus `payform-2.0/QA/AI-GEN-TESTS`, файл `test_case_generator/backend/app.py` (выгрузка CSV); склонировать по HTTPS. Колонки — как в нём: `ID, Name, Description, Precondition, Scenario, Expected result, Priority, Status`; `Status = Draft`. Шаги — в `Scenario` (способ склейки — у генератора QA через запятую без нумерации; исполнитель проверяет на живом Allure TestOps, что нумерованные шаги с переводами строк импортируются лучше, и выбирает). Тело запроса — внутри шага текстом. *Решение Claude:* `ID` в CSV — с ключом задачи (`PF2-3964-TC-03`), чтобы кейсы разных задач не совпадали в общем проекте Allure. Allure сейчас недоступен (после аварии): проверку импорта на живом Allure делает заказчик, когда Allure поднимется; до этого — CSV по эталону генератора QA.

## 10. Артефакты QA в папке задачи

```
tasks/<KEY>/qa/
  cases.md            — кейсы
  questions.md        — вопросы QA аналитику (Q-QA-xx)
  review.md           — замечания ревью (QV-xx) и матрица покрытия
  allure-import.csv   — выгрузка для ручного импорта
  proposals/          — предложения для кейсов с правкой человека
```

Состояние QA (хэши входов, хэши кейсов, отметки «правка человека», снимок строк ТЗ, что выгружено) — исполнитель выбирает: отдельный `qa/state.json` или раздел в общем `state.json`. Решение Claude по умолчанию — отдельный `qa/state.json`, чтобы QA не писали в файлы аналитика.

Вопросы QA аналитику — в `qa/questions.md` (не в общий `questions.md`), формат тот же. Аналитик видит их через `/tdd-status`; ответ переносит в свой журнал решений и, если меняется ТЗ, — `/tdd-update`, после чего QA запускают `/qa-update`.
