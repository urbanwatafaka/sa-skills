# Схемы артефактов задачи

Эталонный пример всех артефактов: `tests/fixtures/LKP-DEMO/` в репозитории плагина.

## Общие правила

- Папка задачи: `tasks/<KEY>/` в рабочей папке аналитика.
- Артефакты — markdown. Данные — в таблицах, проза — только там, где без неё нельзя.
- Шапка (frontmatter) — плоский YAML: `ключ: значение`. Значение — строка, целое, `true`/`false` или список `[a, b]`. Вложенных структур нет.
- ID: `R-01` (пункт BRD), `IM-01` (карта влияния), `Q-PO-01` и `Q-SA-01` (вопросы), `D-01` (решения), `RV-01` (замечания ревью); для QA — `TC-01` (тест-кейс), `U-01` (единица покрытия), `Q-QA-01` (вопрос QA аналитику), `QV-01` (замечание ревью кейсов). Минимум две цифры, сквозная нумерация в задаче, ID не переиспользуются.
- Пустое значение ячейки — `—`.
- ID уникальны внутри артефакта.
- Ссылки (`R-xx`, `IM-xx`, `Q-PO-xx`, `Q-SA-xx`) должны указывать на ID, существующие в соответствующем артефакте (если этот артефакт есть в задаче).

## sources/BRD.md

Шапка: `source` (ссылка или `manual` — при ручном режиме по `shared/access/adapters.md`), `fetched` (ГГГГ-ММ-ДД), `brd_complete` (`true`/`false`), `missing` (список коротких названий недостающих пунктов из `shared/rules/brd-checklist.md`; при `brd_complete: false` не пуст).

Таблица:

| Колонка | Значение |
|---|---|
| ID | `R-xx` |
| Требование | Формулировка из BRD, сжатая без потери смысла |
| Тип | `функц.`, `UI`, `данные`, `интеграция`, `НФТ`, `ограничение` |

## impact-map.md

Шапка: `index_used` (`true`, если использовался индекс `/docs`), `confidence_cap` (`высокая`, `средняя`, `низкая` — потолок уверенности; без индекса не выше `средняя`).

Таблица:

| Колонка | Значение |
|---|---|
| ID | `IM-xx` |
| Объект | `<сервис>: <что именно>` — метод, модуль, таблица, топик, экран |
| Вид | `процесс`, `сервис`, `модуль`, `API`, `Kafka`, `БД`, `роль`, `UI`, `конфиг` |
| Влияние | `новый`, `изм.`, `удал.`, `?` |
| ← R | Один или несколько `R-xx` через запятую |
| Источник | По формату из `shared/rules/ai-rules.md`; `—`, если источника нет |
| Статус | `факт` (есть источник) или `допущение` |
| Уверенность | `высокая`, `средняя`, `низкая` |

- Если `sources/BRD.md` с `brd_complete: true` есть, а `impact-map.md` нет — ошибка: карта должна быть построена.
- Если `impact-map.md` нет, любая ссылка `IM-xx` в `questions.md` или `context.md` — ошибка.

## context.md

Контекст-пакет стадии `/tdd-start`. Шапка: `template` (тип ТЗ и версия шаблона, совпадает с `state.json`), `release` (релиз или срок), `po` (кто PO). Необязательные ключи для заголовка и «Статусов» ТЗ: `title` (название доработки; нет — `<title манифеста>: <KEY>`), `task_status` (`в аналитике`, `в оценке`, `в разработке`, `в стабилизации`; нет — `в аналитике`), `jira` (голый URL задачи; нет — URL собирается из ключа задачи), `design` (ссылка на дизайн; нет — `Не требуется`), `confluence` (pageId опубликованной страницы, пишет публикация).

Типы ТЗ: `feature` — доработка существующих сервисов; `integration` — подключение внешней системы или платёжного метода. Версию задаёт `/tdd-start` из манифеста `shared/templates/<тип>.yaml` (`python3 <плагин>/scripts/sa_template.py version <тип>`); для `integration`, пока манифест не заведён, — `1.0`. `release` и `po` обязательны и непусты.

Обязательные разделы: `## Цель` (1–3 предложения: что и зачем) и `## Границы` (таблица ниже). Необязательные: `## Ограничения`, `## Допущения`, `## Ссылки` — пункты списком, каждый со ссылкой на `R-xx`, `IM-xx` или `D-xx`, где это применимо.

| Колонка | Значение |
|---|---|
| ← IM | Ровно один `IM-xx` из карты влияния |
| Скоуп | `в скоупе`, `вне скоупа`, `?` |
| Комментарий | Причина для `вне скоупа` (обязательна); для `?` — ID вопроса, который это решит; иначе `—` |

- Каждый `IM-xx` из `impact-map.md` встречается в «Границах» ровно один раз.
- `?` — скоуп не решён: на такой пункт заведён вопрос, его ID — в Комментарии.
- Строки меняет команда `python3 <плагин>/scripts/sa_context.py scope tasks/<KEY> <IM-xx…> "<в скоупе|вне скоупа|?>" ["<комментарий>"]`: правит строку на месте, а пункт карты, которого в таблице нет, дописывает в конец. Для `вне скоупа` нужна причина, для `?` — ID вопроса в комментарии.

## questions.md

Две секции, заголовки строго такие: `## Для PO` и `## Для аналитика`. Вопрос — пункт списка:

```markdown
- **Q-PO-01** [R-01] Текст вопроса
  Варианты: а) …; б) … — *open*
```

- Первая строка: ID жирным, ссылки в квадратных скобках (`R-xx`, `IM-xx`, через запятую), текст.
- У каждого вопроса есть хотя бы одна ссылка в квадратных скобках.
- Псевдо-ссылка `[BRD]` — для вопросов PO о недостающих обязательных пунктах BRD (`shared/rules/brd-checklist.md`): `[BRD]` или `[BRD, R-01]`. В `Q-SA` она недопустима, на существование ID не проверяется и сама считается ссылкой.
- Любой другой токен в скобках, не являющийся ID, — ошибка валидатора.
- В тексте и строках продолжения вопроса PO нет ссылок `R-xx`, `IM-xx`, `D-xx`, `RV-xx` — они только в скобках в начале; ссылки на другие вопросы (`Q-PO-xx`) допустимы.
- Продолжение — строки с отступом.
- Статус — в конце любой строки вопроса: `— *open*`, `— *answered*`, `— *obsolete*`; блокирующий открытый вопрос: `— *open, blocking*`.
- `Q-PO-xx` лежат только в секции PO, `Q-SA-xx` — только в секции аналитика.
- Строка продолжения `Согласование: бизнес`, `Согласование: архком` или `Согласование: бизнес, архком` — ответу нужно формальное согласование: бизнеса (риск, деньги, процесс) и/или архитектурного комитета (техническое решение). В ТЗ становится строкой `❗**Требует согласования:** Бизнес, Архитектурный комитет` между вопросом и «Ответ:». Другие значения — ошибка валидатора.
- Строка продолжения `Ответ в ТЗ: <текст>` — ответ, который показывается в «Открытых вопросах» после «**Ответ**:». Ставится, когда для факта нет естественного места в тексте ТЗ: у `answered` — вопрос остаётся в разделе с этим ответом; у `open` — предварительный ответ («предварительно — X; согласования пока не было»). У `obsolete` — ошибка валидатора.
- Существующий вопрос меняют только командами, текст вопроса они не трогают:
  - `python3 <плагин>/scripts/sa_questions.py status tasks/<KEY> <answered|obsolete> <Q-xx…>` — закрыть вопрос; маркер меняется на той строке, где стоит;
  - `python3 <плагин>/scripts/sa_questions.py answer tasks/<KEY> <Q-xx> "<текст>"` — записать или заменить строку `Ответ в ТЗ`;
  - `python3 <плагин>/scripts/sa_questions.py unblock tasks/<KEY> <Q-xx> <D-xx>` — `open, blocking` → `open`, когда решили не ждать ответа: в `decisions.md` должно быть решение `D-xx` с `← Q` = этот вопрос. Вопрос за строкой `?` в «Границах» так не снимается — он остаётся блокирующим. Предварительный ответ — `answer`.

## draft/ и draft.md

Черновик ТЗ стадии `/tdd-draft`. Секции и их порядок задаёт манифест `shared/templates/<тип>.yaml` (тип — из `template` в `state.json`).

- `draft/<id секции>.md` — по файлу на секцию манифеста; других `.md` в `draft/` нет. Первая строка — заголовок секции: `# <title>`, для секции с `level: 2` — `## <title>`.
- Обязательная секция есть всегда. Необязательная без содержания не создаётся: заглушки «Не применимо», «Изменения не требуются», «Без изменений» валидатор отклоняет в любой секции.
- Трассировка — `‹R-01, IM-02, D-01›` после утверждения: внутри только существующие `R-xx`, `IM-xx`, `D-xx` через запятую.
- Неизвестное — плейсхолдер `⚠ Q-PO-xx` или `⚠ Q-SA-xx`: ID открытого вопроса из `questions.md`. Символ `⚠` — только для плейсхолдеров. Вопрос закрыт — плейсхолдер заменяют текстом по решению. `/tdd-status` считает плейсхолдеры по секциям.
- Ссылка «п.N» должна вести на существующий пункт верхнего уровня этой секции или «Доработок»; висячая — ошибка валидатора.
- Ссылки на код вида `код: <путь>:<строка>` / `code: <путь>:<строка>` в секциях запрещены — они живут в карте влияния и `sources/`.
- Диаграмма — файл `draft/diagrams/<id секции>-<вид>.puml` (`@startuml` … `@enduml`) и строка `@diagram diagrams/<файл>.puml` в секции, на отдельной строке. Валидатор проверяет структуру и правила вида по суффиксу имени: `-sequence` — `autonumber "<b>[000]"`, без `alt`/`loop`/`opt`, нет стрелок из участника `queue` (Kafka), а отсылки `**Шаг(и) [00X]-[00Y]**` под диаграммой (до следующего `@diagram` или `:::`) не выходят за число её шагов и покрывают каждый шаг — номера печатает `sa_puml.py steps <файл>`; `-c2` — `linetype ortho`, связи `Rel_D/U/L/R`, подпись каждой связи начинается с номера `N)`, у связи с `$tags="kafka"` — `N) Kafka: <топик> — <Событие>`, подпись «Kafka: …» без тега — ошибка, узел `SystemQueue` (Kafka) — предупреждение; `-er` — `hide circle`; везде — `!include` только с `https://`, `<color:…>` без `#` перед именем цвета и без `
` внутри одного тега.
- OpenAPI — файл `draft/api/<сервис>.yaml` и строка `@openapi api/<сервис>.yaml`. Валидатор проверяет `openapi: 3.0.3`, `info.title` на `.Api`, `info.version` и префикс каждого пути: `/api`, `/backoffice`, `/public`, `/internal`; путь без префикса шлюза (после префикса раздела нет второго префикса или версии `/v1`); тег операции, если указан, совпадает с префиксом (`/api` → `Api`, `/backoffice` → `Backoffice`, `/public` → `Public`, `/internal` → `Internal`).
- DTO сообщения Kafka — файл `draft/dto/<Имя>.json` (JSON с полем `$type`) и плейсхолдер `{{DTO:<Имя>}}` в ячейке таблицы.

`draft.md` собирает только команда `python3 <плагин>/scripts/sa_draft.py assemble tasks/<KEY> [автор]`: шапка, заголовок `# <title из context.md>`, созданные секции по порядку манифеста (перед секцией `level: 2` — `---`), в конце `# Открытые вопросы` — нумерованный список открытых вопросов `questions.md` и закрытых со строкой `Ответ в ТЗ` в формате `Вопрос?<br/>**Ответ**: <ответ в ТЗ>`, при `Согласование` — со строкой `<br/>❗**Требует согласования:** …` перед «Ответ» (нет таких вопросов — раздела нет). Строка `@diagram` заменяется блоком `plantuml`, `@openapi` — блоком `openapi`. Шапка: `status` (`черновик`), `author`, `jira` (ключ задачи), `template` (как в `state.json`), `assembled` (ГГГГ-ММ-ДД). Рядом — `draft-publish.md` для Confluence: «Оглавление» (`:::expand Оглавление` с `{{toc}}`), жирные «Статусы» между `---` (Статус задачи, Автор документа, Jira ссылка — `jira` из `context.md` или голый URL `<JIRA_BASE_URL>/browse/<KEY>`, по умолчанию `https://jira.tasktracker.help`, Ссылка на дизайн), без трассировки, плейсхолдеры `⚠ Q-xx` заменены на `:question:`, в «Открытых вопросах» без ID. `draft.md` руками не правят: валидатор сверяет его со сборкой из секций.

`assemble` записывает в `state.json` `sections.<id>.hash` и снимок `rows` (sha1 строк `R-xx`, `IM-xx`, `D-xx` на момент сборки — по нему `/tdd-update` находит изменения). Стадия, записавшая или поправившая секцию, сразу вызывает `python3 <плагин>/scripts/sa_draft.py mark tasks/<KEY> <секция>` — в `sections.<id>.generated` попадает sha1 её текста. Секция — правка человека (`edited_by_human: true`), если её sha1 не совпадает ни с `hash`, ни с `generated`; это ставят `sa_draft.py plan` и `assemble`, и стадии такую секцию не перезаписывают. Снять отметку — только по слову аналитика: `sa_draft.py release tasks/<KEY> <секция>`.

Плейсхолдер `⚠ Q-xx` на закрытый (answered/obsolete) вопрос валидатор не отклоняет: такие плейсхолдеры показывает `sa_draft.py gaps` («Плейсхолдеры на закрытые вопросы»), заменяет их `/tdd-update`.

Валидатор требует `draft.md`, если есть `draft/` или стадия `draft`, `check`, `done`.

`proposals/<id секции>.md` — предложение `/tdd-update` для секции с правкой человека; `sa_update.py diff|apply|drop tasks/<KEY> <секция>` показывает, принимает (по слову аналитика) или отклоняет его. Валидатор `proposals/` не проверяет.

## review.md

Замечания стадии `/tdd-check`. Шапка: `draft` (sha1 `draft.md`, по которому делалось ревью), `reviewed` (ГГГГ-ММ-ДД), `round` (номер прохода ревью, с 1).

```markdown
## Замечания

| ID | Важность | Где | Проблема | ← Ссылка | Предложение | Статус |
|---|---|---|---|---|---|---|
| RV-01 | критично | 01-brd | R-04 (функц.) не покрыт ни одним критерием приёмки User Stories (есть в 03-changes) | R-04 | добавить критерий со ссылкой ‹R-04› в таблицу User Stories | открыто |

## Покрытие BRD

| R | Секции | Истории |
|---|---|---|
| R-04 | 03-changes | — |
```

| Колонка | Значение |
|---|---|
| ID | `RV-xx`, сквозная нумерация, не переиспользуются |
| Важность | `критично`, `важно`, `совет`; замечание без доказательства — `совет` |
| Где | id секции из манифеста, `шапка` или `весь черновик` |
| Проблема | Что не так, с коротким доказательством (цитата, номер истории в таблице User Stories или шага) |
| ← Ссылка | `R-xx`, `IM-xx`, `D-xx`, `Q-PO-xx`, `Q-SA-xx` через запятую; `—` — для замечаний по шаблону; существование ID валидатор проверяет только в строках `открыто`; в `принято`, `отклонено`, `закрыто` ссылка на исчезнувший ID допустима, строку не правят |
| Предложение | Как исправить |
| Статус | `открыто` (новое), `принято` / `отклонено` (решение аналитика), `закрыто` (повторный `/tdd-check` не нашёл проблему) |

- Матрица «Покрытие BRD» — вывод `python3 <плагин>/scripts/sa_review.py coverage tasks/<KEY>` как есть: каждый `R-xx` из BRD ровно один раз; `Секции` — где `R-xx` есть в трассировке, `Истории` — строки таблицы User Stories («история N», по порядку), в критериях приёмки которых есть ссылка на него; кодов `US-xx`/`AC-xx` в ТЗ нет. Пока `draft` в шапке совпадает с sha1 `draft.md`, валидатор сверяет матрицу с черновиком (полнота по `R-xx` из BRD, секции и истории); у устаревшего `review.md` проверяются только дубли `R`.
- Файл пишет только команда `python3 <плагин>/scripts/sa_review.py write tasks/<KEY> <файл.json>`, JSON — `{"new": [{"severity", "where", "problem", "ref", "proposal"}], "close": ["RV-xx"]}`: `new` — замечания ревьюера и сверки с кодом, `close` — прошлые `открыто`/`принято`, которые ревьюер признал закрытыми. Команда сама добавляет замечания `precheck` и закрывает те из них, которых `precheck` больше не находит; закрывает `открыто` со ссылкой на исчезнувший ID; пропускает дубли прошлых `открыто`/`принято`/`отклонено` (та же Где и Проблема); выдаёт ID новым; пишет шапку (`draft`, `reviewed`, `round` + 1) и матрицу покрытия. `|` в тексте заменяется на `¦`.
- Статус меняет только команда `python3 <плагин>/scripts/sa_review.py status tasks/<KEY> <принято|отклонено> <RV-xx…|все>` (`все` — все `открыто`); `закрыто` ставит только `/tdd-check`. ID и тексты прошлых замечаний не меняются.
- На стадии `check` и `done` файл обязателен.

## decisions.md

| Колонка | Значение |
|---|---|
| ID | `D-xx` |
| ← Q | `Q-PO-xx` / `Q-SA-xx`, или `—`, если решение принято без вопроса |
| Решение | Что решили, одной-двумя фразами |
| Кто/где | Кто принял и где зафиксировано: «PO, чат ММ», «разработка, MR !123» |
| Дата | ГГГГ-ММ-ДД |

## state.json

```json
{
  "task": "LKP-4155",
  "stage": "clarify",
  "template": "feature@1.0",
  "plugin_version": "0.1.0",
  "access": {"jira": "mcp", "confluence": "cli", "git": "cli"},
  "inputs": {"BRD": "<sha1>"},
  "sections": {"05-api": {"hash": "<sha1>", "edited_by_human": false}}
}
```

- `task`: непустая строка с ключом задачи.
- `plugin_version`: формат `x.y.z`.
- `stage` — последняя отработавшая стадия (`clarify` может запускаться повторно): `impact`, `start`, `clarify`, `draft`, `check`, `done`. `/tdd-clarify` после `draft`/`check` стадию не откатывает.
- `template`: появляется на стадии `start`, формат `имя@мажор.минор`.
- `access`: выбранный режим доступа (`mcp`, `cli`, `manual`) по `shared/access/adapters.md`. Ключи — только `jira`, `confluence`, `git`.
- `inputs`: ключи — только имена артефактов `BRD`, `impact-map`, `context`, `questions`, `decisions`, `draft`, `review`; значения — sha1. sha1 входных артефактов на момент, когда их последний раз использовала стадия. Записывать командой `python3 <плагин>/scripts/sa_state.py record <папка задачи> <артефакт>...`.
- `sections`: для каждой секции `hash` (sha1), `edited_by_human` (`true`/`false`), необязательный `generated` (sha1 текста, записанного стадией).
- `rows`: снимок `ID → sha1` строк BRD, карты и решений на момент последней сборки; пишет `assemble`.
- `published`: `{"url": <ссылка>, "hash": <sha1 draft-publish.md>, "version": <версия страницы>}` — страница опубликована; пишут `sa_state.py set <папка задачи> published <ссылка>` и `… published.version <версия>`. Перед повторной публикацией текущую версию страницы сравнивают с `version`: выросла — страницу правили руками, ручные правки переносят по `shared/access/adapters.md`.
- `code_check`: sha1 `draft.md`, сверенного с кодом последним `/tdd-check --code`; пишет `sa_state.py set <папка задачи> code_check draft`. Не совпадает с текущим `draft.md` — статус предлагает финальную сверку с кодом перед завершением.
- Счётчики вопросов здесь не хранятся: их считают по `questions.md`.

Создавать и менять состояние — только командами, не правкой JSON вручную:

```bash
python3 <плагин>/scripts/sa_state.py init <папка задачи> <KEY>                # создать state.json, stage: impact
python3 <плагин>/scripts/sa_state.py set <папка задачи> stage clarify         # stage, template, access.<jira|confluence|git>
python3 <плагин>/scripts/sa_state.py set <папка задачи> access.jira mcp
python3 <плагин>/scripts/sa_state.py set <папка задачи> published <ссылка>      # страница опубликована
python3 <плагин>/scripts/sa_state.py set <папка задачи> published.version 7   # версия опубликованной страницы
python3 <плагин>/scripts/sa_state.py record <папка задачи> BRD impact-map     # хэши входных артефактов
```

## qa/

Артефакты стадий QA (`/qa-cases`, `/qa-check`, `/qa-export`, `/qa-update`). Стадии QA пишут только в `tasks/<KEY>/qa/`; файлы аналитика не меняют. Правила написания кейсов — `shared/rules/qa-cases.md`.

| Файл | Что | Кто пишет |
|---|---|---|
| `cases.md` | тест-кейсы | `/qa-cases`, `/qa-update`, человек |
| `units.md` | единицы покрытия `U-xx` | `sa_qa.py units`; статусы — стадия и человек |
| `questions.md` | вопросы QA аналитику `Q-QA-xx` | `/qa-cases`, `/qa-update` |
| `review.md` | замечания ревью `QV-xx` и матрица покрытия | `/qa-check` |
| `allure-import.csv` | выгрузка для ручного импорта в Allure TestOps | `sa_qa.py export` |
| `proposals/` | предложения для кейсов с правкой человека, `<TC-xx>.md` | `/qa-update` |
| `state.json` | хэши кейсов, снимок строк ТЗ и единиц, что выгружено | `sa_qa.py mark`, `sa_qa.py export` |

### cases.md

Заголовок `# Тест-кейсы <KEY>`, разделы `## Бэкенд`, `## Фронт`, `## Регресс`. Кейс — подраздел `### TC-xx <название>` строгого формата из `shared/rules/qa-cases.md`: строки `- **Вид:**`, `- **Приоритет:**`, `- **Покрывает:**`, `- **Источник:**` и блоки `**Описание:**`, `**Предусловия:**`, `**Шаги:**`, `**Ожидаемый результат:**`. Вид — `бэкенд`, `фронт`, `регресс`; приоритет — `High`, `Medium`, `Low`. Кейс, добавленный руками без `TC-xx`, получает ID при следующем запуске стадии. Удалённый руками кейс стадии не восстанавливают.

### units.md

| ID | Где | Пункт | Статус | Причина |
|---|---|---|---|---|

- Где — место в ТЗ: `01-brd/story-<n>/<k>`, `01-brd/ui/<n>`, `03-changes/<сервис>/Back/<1.3.2>`, `03-changes/<сервис>/Front/<экран>/<1.2>`, `08-testing/new/<n>`, `08-testing/keep/<n>`.
- Пункт — текст пункта ТЗ с трассировкой `‹…›`; `|` в тексте заменён на `¦`.
- Статус: пусто (тестируется), `не поведение`, `не тестируется`, `нужно решение`, `удал.`. Кроме пустого и `удал.`, причина обязательна.
- Таблицу пишет только `sa_qa.py units`: пункт переформулирован или сдвинулся — `U-xx` сохраняется; пропал — `удал.`; статус и причину скрипт не перезаписывает. Человек и стадия меняют только колонки Статус и Причина.

### questions.md

Формат как у `questions.md` задачи, один раздел `## Для аналитика`, ID `Q-QA-xx`: `- **Q-QA-01** [D-13] <вопрос> — *open*`. Ответ аналитик переносит в свой `decisions.md`; при изменении ТЗ — `/tdd-update`, затем QA — `/qa-update`.

### review.md

Шапка: `cases` (sha1 `cases.md`), `reviewed` (дата), `round`. Разделы `## Замечания` — таблица `| ID | Важность | Кейс | Проблема | ← Ссылка | Предложение | Статус |` (важность `критично`/`важно`/`совет`; статус `открыто`/`принято`/`отклонено`/`закрыто`) и `## Покрытие` — вывод `sa_qa.py coverage`.

### allure-import.csv

Колонки: ID, Name, Description, Precondition, Scenario, Expected result, Priority, Status. Кодировка UTF-8 с BOM. `ID` — `<KEY>-TC-xx`, `Status` — `Draft`, `Scenario` — шаги «1. …» через перевод строки, тело запроса — внутри шага.

### state.json

`{"cases": {TC: {"generated": sha1, "exported": sha1 | null, "refs": {ID: sha1}}}}`. `refs` — снимок строк `R/IM/D` из «Источника» и единиц из «Покрывает» на момент `mark` этого кейса: по нему `affected` находит задетые кейсы. ID кейсов из `cases` не переиспользуются, даже если кейс удалён из `cases.md`. `generated` не равен хэшу кейса — правка человека: стадии такой кейс не перезаписывают, а кладут предложение в `proposals/`. Править только командами `sa_qa.py mark` и `sa_qa.py export`.

## Проверка

После записи любого артефакта стадия запускает:

```bash
python3 <плагин>/scripts/sa_validate.py tasks/<KEY>
```

`OK: …` — можно продолжать. Иначе исправь каждую строку ошибки и запусти снова. Не сообщай о завершении стадии, пока валидатор не вернул `OK`.
