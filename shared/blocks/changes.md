## Правила

- Группировка — только по сервисам, заголовок `##` — жирная ссылка на git-репозиторий сервиса. Сервисы — из колонки «Объект» карты влияния в скоупе. Порядок — по ходу сценария.
- Сразу под заголовком сервиса строка `Задача: <ссылка на Jira>` голым URL или `Задача: &lt;Не заведена&gt;`.
- Внутри сервиса порядок `### Front` → `### Back`; создаётся только тот, где есть изменения.
- `Front` без своего текста, сразу под ним — `### Экран: <название>` с тремя строками-ключами жирным: **URL:**, **Доступен для ролей:**, **Что изменить:** (нумерованный список).
- **URL:** — путь существующего экрана, путь, который уже заготовила разработка, или `новый`, если экрана ещё нет и путь не задан. Путь не придумывай.
- Действия в строке списка — по статусам: вложенный список «статус → кнопки → метод», одинаково во всех клиентах (ЛК, БО). Образец с условными именами: `Pending` — «Повторить» (`POST /api/<сущность>/{id}/resend`), «Отозвать» (`POST /api/<сущность>/{id}/disable`); `Approved` — кнопок нет.
- `Back` — всегда ровно три подпункта: **1. Описание изменений:**, **2. API:**, **3. БД:**.
- «1. Описание изменений» в Back и «Что изменить» на экране Front — нумерованный список по одним правилам. Пункт = короткий заголовок (метод, сущность, команда, топик), содержание — нумерованными подпунктами под ним. Одна мысль — один подпункт; последствия — вложенными подпунктами под действием; порядок подпунктов = порядок выполнения: проверки доступа (`403`/`422`) → действие → запись полей → письма и события. Короткое действие из одной фразы — одной строкой.
- Пункт начинается сразу с действия («Новый метод…», «Убрать фильтр…»), без пересказа текущего поведения. Текущее поведение — только одной оговоркой, если оно обосновывает действие.
- Ссылка на другой пункт — «(п.16)». Номера пунктов верхнего уровня при правке не сдвигаются: новый пункт — в конец списка сервиса, удалённый — не перенумеровывает остальные без сверки. После любой правки проверь, что каждая «п.N» ведёт туда же, куда раньше.
- Один метод или сущность — один пункт. Правки одного метода, в том числе ради разных процессов, собираются подпунктами под ним, а не разносятся по разным пунктам.
- По каждому пункту проверь, применимы ли: приоритеты, наследование, пустое значение и значение по умолчанию, расчёт, исторические данные (что с записями до релиза), ошибки. Применимо — опиши подпунктом; неприменимо — не пиши механически. Нет решения — `⚠ Q-…`, а не общая фраза.
- Прежде чем спроектировать новый метод, проверь по коду сервиса-получателя (`sa-skills:source-reader`), нет ли подходящего. Есть похожий, но не подходит по контракту или авторизации — одной строкой в пункте, почему нужен новый.
- Новый метод — вложенным маркированным списком его поля: имя, тип, обязательность, назначение. Изменённый метод — какие поля добавляются и какие исключаются; поля не меняются — «Изменений полей нет».
- Новое значение существующего enum — английское имя по стилю существующих значений рядом с русской подписью, с пометкой «предложено, подтвердить при реализации». Вычисляемое поле API — с маппингом «значение ← `Enum.Значение`» в пункте и коротко тот же маппинг в `description` этого поля в OpenAPI.
- Описывай результат, а не правку исходников: без файлов, классов, обработчиков, BackgroundService, outbox, атрибутов. Можно: сервисы, методы, поля, статусы, права, топики, коды шаблонов.
- Вместо «расширить справочник» — перечисли значения и их смысл; вместо «обновить валидацию» — допустимые сочетания и результат отказа; вместо «обеспечить передачу» — источник, получатель и поля.
- Метод — `ГЛАГОЛ /префикс/путь`; префикс раздела обязателен: `/api` (фронт ЛК), `/backoffice` (БО), `/public` (без авторизации), `/internal` (между сервисами). Общий метод для ЛК и БО — два пути с разными префиксами. Путь — как объявлен в сервисе, без префикса шлюза: `/backoffice/orders`, не `/api/backoffice/v1/orders`. Маршрут в сервисе объявлен без префикса, а раздел задаёт группа Swagger (`ApiExplorerSettings(GroupName = "api")`), — префикс берётся из группы: группа `api` и маршрут `files/upload-url` → `POST /api/files/upload-url`.
- Тестовый метод (группа Swagger `test` и другие методы только для стендов) — пунктом «Описания изменений» текстом: путь как в сервисе, без префикса раздела, без OpenAPI и без строки в `@openapi`-файле; назначение и где доступен.
- «2. API» — при любой REST-доработке сервиса: строка `@openapi api/<сервис>.yaml`, файл `draft/api/<сервис>.yaml` — один валидный OpenAPI на сервис: `openapi: 3.0.3`, `info.title` = .NET-неймспейс в PascalCase + `.Api` (`payform.prodamusid.userprofile` → `Payform.ProdamusId.UserProfile.Api`), `info.version`, `paths` на все затронутые методы, включая изменённые без правки полей, кроме тестовых. Несколько разделов — `tags` (`Api`/`Backoffice`/`Public`/`Internal`) в шапке и `tags: [<Раздел>]` у операций. Нет REST-доработки — по образцу «3. БД»: «Изменений API не требуется — <причина>».
- «3. БД» — ER-диаграмма изменений `@diagram diagrams/03-changes-er.puml` (новое — `<color:red>`) или предложение «Изменений схемы БД не требуется — <причина>».
- Kafka-топики здесь не описываются таблицей: в пункте сервиса — короткое «подключить консьюмер, см. «Топики Кафка»», таблица — в `04-kafka`.
- Неподтверждённое кодом или аналитиком техническое предположение — первым предложением бизнес-эффект, затем `:::expand В технической реализации это будет (нагенерено, не проверила):` … `:::`. Формулировку заголовка не меняй; пометку снимает только аналитик. Для проверенных фактов этот блок не используй.
- Ссылки `файл:строка` и `код:` в секцию не переносятся — они остаются в `sources/` и карте влияния.

## Чек-лист

- [ ] Каждый `IM-xx` в скоупе с влиянием `новый`/`изм.`/`удал.` есть хотя бы в одном пункте.
- [ ] У каждого сервиса — ссылка на репозиторий и строка `Задача:`.
- [ ] У каждого `Back` — три подпункта «1. Описание изменений» / «2. API» / «3. БД».
- [ ] Пункты «Описания изменений» и «Что изменить» — заголовок + подпункты, без длинных абзацев через точку с запятой.
- [ ] Все пути методов, кроме тестовых, с префиксом `/api`, `/backoffice`, `/public` или `/internal` (из маршрута или группы Swagger).
- [ ] Для каждой REST-доработки есть `@openapi` и файл проходит `sa_validate.py`.
- [ ] Текст Front и уведомлений не противоречит Back: обещанное на экране («Владелец получит письмо») реально делает бэкенд.
- [ ] Разработчик по каждому пункту поймёт ожидаемый результат без повторного выяснения смысла.
- [ ] Новые методы проверены по коду: подходящего существующего нет.
- [ ] Каждая ссылка «п.N» ведёт на нужный пункт; при правке номера не сдвинулись.
