# Блок: BRD

Секция `01-brd`. Общий стиль — `shared/rules/writing-style.md`.

## Когда

Всегда: первый раздел ТЗ после «Статусов».

## Структура

```markdown
# BRD

## Контекст/Проблема

Партнёры указывают в анкете клиента собственный промокод и получают вознаграждение за свои же транзакции. ‹R-01›

## User Stories

| Контекст | User Story | Критерии приемки |
|---|---|---|
| Анкета клиента в ЛК | Я, **как** Мерчант,<br/>**хочу** не иметь возможности указать собственный промокод,<br/>**чтобы** вознаграждение начислялось только за привлечённых клиентов. ‹R-01› | • Анкета с собственным промокодом не сохраняется ‹R-01›<br/>• Мерчант видит текст ⚠ Q-PO-02 |

## Требования к UI

1. Экран «Анкета клиента» — под полем «Промокод» показать текст ошибки ⚠ Q-PO-02. ‹R-02›

---
```

## Правила

- «Контекст/Проблема» — один короткий абзац (1–2 предложения): в чём проблема именно сейчас и почему нужна эта доработка. Не пересказ задачи и не описание будущего решения: как будет устроено — в «Архитектура и Процесс» и «Доработки».
- В BRD нет деталей реализации: сервисов, методов, полей, таблиц.
- «User Stories» — всегда таблица из трёх колонок: `Контекст`, `User Story`, `Критерии приемки`. Код `US-xx` не нужен.
- В ячейке User Story — три строки через `<br/>`: «Я, **как** <роль>,» / «**хочу** …,» / «**чтобы** …». Жирные только «как», «хочу», «чтобы». Без обратных кавычек.
- Роль — строго из списка: КС, Мерчант, Плательщик, бухгалтер, юрист, продакт/владелец системы. Не «система» и не сервис: для бэкенд-истории роль — тот, кому нужен результат. Неочевидно, какая подходит, — `Q-PO` со списком ролей.
- Критерии приемки — маркированный список в ячейке (`•` через `<br/>`), каждый проверяем: условие → результат, без оценочных слов.
- В критериях приемки нет регресса: ни метки «Регресс», ни пунктов «работает как сейчас». Сохраняемое поведение — только в `08-testing`.
- Каждый `R-xx` типа `функц.` или `UI` покрыт хотя бы одной строкой таблицы со ссылкой в `‹…›`.
- «Требования к UI» — только если UI меняется; иначе подраздела нет. Требования конкретные: экран, элемент, текст в «ёлочках».
- Последняя строка секции — горизонтальная черта `---`.

## Чек-лист

- [ ] «Контекст/Проблема» — 1–2 предложения о проблеме, без решения.
- [ ] User Stories — таблица Контекст / User Story / Критерии приемки, роли из списка.
- [ ] Каждый `R-xx` типа `функц.`/`UI` есть в ссылках хотя бы одной истории.
- [ ] В критериях приемки нет регресса.
- [ ] «Требования к UI» есть только при изменении UI.
