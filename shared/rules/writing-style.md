# Стиль текста ТЗ и артефактов

Стиль взят из эталонных ТЗ команды (Confluence pageId 110167390, 110166633). Цель — текст, который разработчик читает один раз и делает по нему без уточнений. Структура ТЗ — манифест `shared/templates/feature.yaml` и блоки `shared/blocks/`.

## Общие правила

- Суть сначала, подробности потом: каждый блок начинается с одного-двух предложений о том, что меняется и зачем.
- Одна мысль — один пункт. Текст длиннее абзаца — списком: нумерованным, если важен порядок, иначе маркированным.
- Имена сервисов, методов, полей, таблиц, топиков, enum — как в коде, `моноширинным`: `partners-dashboard`, `GET /internal/users/find`, `lkp.questionnaires`.
- Метод — HTTP-глагол заглавными, пробел, полный путь с `/` и префиксом раздела (`/api`, `/backoffice`, `/public`, `/internal`), как он объявлен в сервисе: `GET /backoffice/orders/refunds`. Не путь через шлюз (`/api/backoffice/v1/orders/refunds`) и не путь без префикса. Маршрут объявлен без префикса — префикс из группы Swagger метода. Тестовый метод (только для стендов) — путь как в сервисе, без префикса раздела. Таблица БД — слитно `схема.таблица`.
- Тот, кто платит, — всегда **плательщик**, не «покупатель», «пользователь», «клиент».
- Тексты, которые увидит пользователь, — в «ёлочках», дословно.
- Числа и границы — точные: «до 25 символов», «кэш 10 минут».
- Термин, без которого не понять ТЗ, объясняется при первом употреблении; отдельного «Глоссария» в ТЗ типа 1 нет. Где глоссарий нужен — только таблица «Термин | Значение», термин не жирный.
- Значения в таблицах — моноширинным. «Ключ — значение» — ключ жирным, значение обычным текстом.

## Тон

- Текст — подсказка коллеге, не протокол: прямо и по-деловому.
- Без пассива и безличных оборотов («было проверено», «проверка показала», «выяснилось»): инфинитив («верить примеру, не сваггеру») или, где нужно сказать о проверке, первое лицо («проверила», «сопоставила»). Первое лицо — редко: обычно хватает инфинитива или прямого утверждения.
- Нижняя граница: без обращения на «ты», без разговорных вставок («эй», «слышь»), без мата.
- Было → стало: «Проверено по реальному Swagger: метод в структурированной схеме не описан, документация внутренне противоречива» → «В сваггере метод не описан — только текстом. Верить примеру, не сваггеру».

## Как есть и как будет

- В тексте ТЗ нет меток `[as is]`/`[to be]`. Новое на диаграммах — красным (`shared/blocks/diagrams.md`), в «Доработках» описывается только то, что строим или меняем.
- Пункт доработки начинается сразу с действия. Текущее поведение — только одной короткой оговоркой, если оно обосновывает действие («текущий метод только ищет пользователя — нужен новый на создание»).
- Сохраняемое поведение — только в «Тестирование и регресс» → «Сохраняемое поведение»: конкретное условие и как именно оно работает.

## Оформление

- Макросы в черновике кодируются блоками: `:::info` … `:::` — справочное, `:::warning` … `:::` — важное, `:::expand <заголовок>` … `:::` — «Раскрыть». Код — fenced-блок с языком (макрос «Код»); SQL — под `:::expand` и в блоке `sql`, длинные `CASE`/условия переносятся на строки.
- Неопределённость в тексте — плейсхолдер `⚠ Q-PO-xx`/`⚠ Q-SA-xx`; при публикации он становится эмотиконом вопроса, а сам вопрос — пунктом «Открытых вопросов». Недостающие данные — `ХХХХХ`, рядом тот же плейсхолдер (кроме паспортной таблицы, где `ХХХХХ` самодостаточен). На диаграммах — текстовое `(?)`.
- User Story — таблица Контекст / User Story / Критерии приемки (`shared/blocks/brd.md`).
- Описание sequence — нумерованный список, в конце каждого пункта `**Шаги [00X]-[00Y]**`.
- REST API — OpenAPI в макросе `open-api` (`shared/blocks/changes.md`). Не-REST (SOAP) — без «Раскрыть»: Метод, Тип (POST/GET), Авторизация, таблицы маппинга на вход и на выход.
- Ссылка на другую страницу Confluence — гиперссылка с анкором, не голый `pageId`. Ссылка на задачу Jira — голый URL, каждая на своей строке (Confluence разворачивает её в виджет).
- Пользователь Confluence (автор и любые упоминания) — ссылка-упоминание, не текст с именем.
- Жирный, курсив, подчёркивание — только для акцента; без эмодзи.

## Запрещённые формулировки

- Оценочные слова без измерения: «удобно», «быстро», «корректно», «оптимально», «при необходимости», «и т.д.».
- Неопределённый субъект: «система обработает» — пиши, какой сервис.
- Рамочные фразы: «стоит отметить, что», «необходимо указать», «следует обратить внимание», «было выявлено». Цепочки пассивных причастий («было проверено, сопоставлено»). Повелительное на «вы» — вместо него инфинитив.
- «Не уточнялось», «не уточнено», «не сообщалось», «требует уточнения», `(?)` в тексте — вместо них «пока нет данных» и плейсхолдер вопроса.
- Ссылки на процесс работы ИИ и раскопок: «отсутствует в репозитории», «не найдено», «согласно конспекту», «как обсуждалось». Исключение — заголовок `В технической реализации это будет (нагенерено, не проверила):`.
- «Аналитик подтвердил», «аналитик попросил» — текст пишется от лица аналитика, факты прямо.
- Заглушки разделов: «Не применимо», «Изменения не требуются», «Без изменений» — раздела без содержания просто нет.
- Детали реализации: имена классов, обработчиков, консьюмеров, мапперов, файлы и строки кода, outbox, `BackgroundService`, атрибуты авторизации. Ссылки `код: файл:строка` живут в артефактах задачи, не в ТЗ.
- Маркеры генерации: «Отличный вопрос», «Давайте рассмотрим», «В заключение».
