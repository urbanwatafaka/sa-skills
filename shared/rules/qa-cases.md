# Правила тест-кейсов QA

Общие для `/qa-cases`, `/qa-check`, `/qa-update`. Формат файлов — раздел «qa/» в `shared/schemas/artifacts.md`.

## Для кого кейс

Кейс читает новичок: опытный тестировщик, который ещё не прошёл онбординг в команду. Тестировать он умеет, но не знает продукт, экраны, методы и данные. Критерий: новичок проходит кейс без вопросов и без чтения ТЗ.

- Называй экран, вкладку, поле и кнопку так, как они подписаны в интерфейсе, и говори, как до них дойти.
- Метод — полностью: глагол, путь, готовое тело запроса.
- Не используй внутренние сокращения команды без расшифровки при первом упоминании в кейсе (ЛК — личный кабинет мерчанта, БО — бэк-офис, КС — сотрудник клиентского сервиса).

## Формат

````markdown
### TC-03 Загрузка логотипа больше 5 МБ отклоняется

- **Вид:** бэкенд
- **Приоритет:** High
- **Покрывает:** U-07, U-21
- **Источник:** ‹R-01, IM-05, D-13›

**Описание:** Метод загрузки файла канала продаж не принимает файл больше 5 МБ.

**Предусловия:** Мерчант с каналом продаж; файл PNG размером 6 МБ.

**Шаги:**
1. Вызвать метод `POST /api/files` с файлом 6 МБ в поле `file`.

**Ожидаемый результат:** Ответ `400`; документ не создан — в `public.Document` нет новой записи.
````

- Заголовок — `### TC-xx <название>`: название — что проверяем и чем кончается, одной фразой.
- Строки полей — ровно `- **Вид:**`, `- **Приоритет:**`, `- **Покрывает:**`, `- **Источник:**`; блоки — ровно `**Описание:**`, `**Предусловия:**`, `**Шаги:**`, `**Ожидаемый результат:**`. Между ними — только пустые строки.
- **Вид:** `бэкенд`, `фронт` или `регресс`.
- **Покрывает:** единицы `U-xx` из `qa/units.md` через запятую — по ним считается покрытие. Только единицы, которые кейс действительно проверяет.
- **Источник:** ID строк ТЗ `‹R-xx, IM-xx, D-xx›` — по ним `/qa-update` находит задетые кейсы. Факт, взятый из кода или индекса `docs/`, а не из ТЗ, — добавь через `;`: `code: <репо>/<путь>:<строка>` или `docs: <репо>/docs/<файл>#<раздел>`; одна ссылка — одна запись через `;`. Пустой «Источник» — ошибка: без него `/qa-update` не найдёт кейс при изменении ТЗ.
- **Шаги:** нумерованный список; тело запроса — fenced-блок `json` внутри шага с отступом в три пробела.
- **Ожидаемый результат:** один, в конце кейса, не после каждого шага.

## Бэкенд-кейс

- Шаг — «Вызвать метод `ГЛАГОЛ /путь`» с готовым телом; инструмент (Swagger, Postman) не называй.
- Ожидаемый результат начинается с кода ответа: «Ответ `400`», «Ответ `201`, в теле `documentId`».
- Проверки вне ответа разрешены — у QA есть доступ к БД, Kafka, Redis: назови таблицу и запись (`public.Document`, запись с `OrderId` из ответа), топик и сообщение, ключ Redis.

## Фронт-кейс

- Шаги по интерфейсу: «Открыть …», «Нажать «Сохранить»», «В поле «Логотип» выбрать файл 6 МБ».
- Тексты сообщений — в «ёлочках» дословно из ТЗ.

## Регресс

Кейсы по «Сохраняемому поведению»: что работало до релиза и должно работать так же. Предусловие говорит, какие данные «до релиза» нужны; если без помощи разработки их на стенде не получить — единица `нужно решение`, кейс не пишется.

## Предусловия

Только условие: «мерчант с каналом продаж», «заявка в статусе «На рассмотрении»». Без стенда, учёток и способа подготовить данные — их новичку выдают отдельно.

## Запрещено

- Расплывчатое в шагах и результате: «корректно», «правильно», «успешно» без уточнения, «проверить, что работает», «и т.д.», «при необходимости». Пиши конкретное значение: код, текст, поле, запись.
- Выдумывать правила, тексты, коды ответов, которых нет ни в ТЗ, ни в решениях, ни в коде. Не знаешь — плейсхолдер `⚠ Q-QA-xx` в кейсе и вопрос аналитику в `qa/questions.md`.
- Писать в файлы аналитика (`draft/`, `decisions.md`, `questions.md` и другие вне `qa/`).

## Приоритет

По умолчанию: `High` — основной сценарий и ошибки из критериев приёмки; `Medium` — остальное новое поведение; `Low` — регресс.

## Единицы покрытия

`qa/units.md` строит скрипт: пункты критериев приёмки, «Требований к UI», «Описания изменений» Back, «Что изменить» Front, «Нового» и «Сохраняемого поведения». Статусы:

- пусто — тестируется, нужен хотя бы один кейс;
- `не поведение` — пункт ничего не проверяет («Тело — `multipart/form-data`», «MD5 не считать»); стадия ставит сама с причиной, человек может снять;
- `нужно решение` — проверку на стенде не устроить без помощи DevOps или разработки (недоступность смежного сервиса, повторы с паузами, выключенные уведомления хранилища, данные «до релиза»); стадия ставит с причиной и кейс не пишет;
- `не тестируется` — ставит только человек, с причиной;
- `удал.` — пункта больше нет в ТЗ, ставит скрипт.
