# Доступ к Jira, Confluence и Git

Каждая система подключается одним из трёх режимов. Режим выбирается при первом обращении к системе в задаче и сохраняется в `state.json`.

## Порядок выбора

1. Если в `state.json` уже есть `access.<система>` — используй его.
2. Иначе пробуй по порядку: `mcp` → `cli` → `manual`.
3. Режим не сработал (нет инструмента, ошибка авторизации, таймаут) — коротко скажи пользователю, что не сработало, и переходи к следующему. Стадия не прерывается.
4. Пользователь может сам назвать режим — тогда используй его.

## Jira

- `mcp`: в списке инструментов есть MCP-инструменты с `jira` или `atlassian` в имени. Получи задачу: описание, статус, связи.
- `cli`: `python3 <плагин>/scripts/sa_fetch.py jira <KEY>` — печатает ключ, summary, статус, связи и описание текстом. Скрипт сам читает `JIRA_BASE_URL`, `JIRA_TOKEN` (для Cloud ещё `JIRA_EMAIL`); не передавай их в командах.

## Confluence

- `mcp`: MCP-инструменты с `confluence` или `atlassian` в имени.
- `cli`: `python3 <плагин>/scripts/sa_fetch.py confluence <id>` — печатает заголовок, версию и тело страницы текстом. Скрипт сам читает `CONFLUENCE_BASE_URL` и `CONFLUENCE_TOKEN`; не передавай их в командах.

- Текст страницы может быть большим. Не держи его в контексте: сразу сохрани выжимку в `sources/confluence-<id>.md` — заголовки, таблицы, ключевые правила со ссылками на разделы.

### Публикация ТЗ

Публикуется только `draft-publish.md` и только в режиме `mcp`. В режимах `cli` и `manual` — путь к файлу для ручной вставки.

1. **Место.** Пространство и родительская страница названы аналитиком явно. Нет хотя бы одного — не публикуй, даже если содержимое уже одобрено, и спроси.
2. **Эталоны.** Перед первой публикацией прочитай storage-формат эталонов pageId 110167390 (весь документ), 110167415 (скелет) и 110166633 (наполнение «Доработок») и любой страницы целевого пространства с нужными макросами — имена и структуру `ac:structured-macro` бери оттуда. Примера для макроса нет — стандартный синтаксис Confluence и одна строка об этом в итоге.
3. **Конвертация** `draft-publish.md` в storage-формат:

   | В файле | В Confluence |
   |---|---|
   | `:::expand Оглавление` + `{{toc}}` | «Раскрыть» с макросом TOC внутри |
   | `**Статусы**` между `---` | жирный текст между `<hr/>`, не заголовок |
   | `:::info` / `:::warning` | «Информация» / «Предупреждение» (`ac:name="warning"`) |
   | `:::expand <заголовок>` | «Раскрыть» с этим заголовком, содержимое — обычная разметка |
   | блок `plantuml` | макрос PlantUML, не картинка и не текст |
   | блок `openapi` | макрос `open-api`, YAML в `ac:plain-text-body`, без параметров; не макрос «Код» |
   | другой fenced-блок | макрос «Код» с языком |
   | `{{DTO:<Имя>}}` | в ячейке `<div class="content-wrapper">` с макросом «Код»: `json`, заголовок `<Имя>`, `collapse=true`, тело — `draft/dto/<Имя>.json` |
   | `:question:` | `<ac:emoticon ac:name="question" />` |
   | автор в «Статусах» | `<ac:link><ri:user ri:username="…"/></ac:link>` |
   | `&lt;Не заведена&gt;` | текст `<Не заведена>` |

   Автор — из учётной записи, под которой идёт публикация; не определяется — спроси имя и логин.
4. **Предпросмотр.** Покажи аналитику результат конвертации (не сырой `.md`) и жди явного «публикуй».
5. **Создание или обновление.** В шапке `context.md` нет `confluence` — создай страницу, запиши `confluence: <pageId>` в шапку `context.md` и повесь метку `ИИ-черновик`. Есть — обновление этой же страницы.
6. **Перед каждым обновлением** — свежий `get_page`. Версия отличается от последней известной — страницу правили руками: сравни живой контент с прошлой публикацией по тексту **и** разметке (списки, вложенные макросы, порядок блоков, эмотиконы) и перенеси ручные правки в новую версию; там, где аналитик правил, живой контент главнее. Субагенту, который сверяет, явно ставь задачу сравнить и разметку.
7. **Проверка после сохранения.** Перечитай storage: сырой `@startuml` или `openapi:` вместо макроса, YAML в «Коде» вместо `open-api`, имя макроса текстом — ошибка, исправь. Пустой `open-api` без тела после первой попытки бывает — проверяй именно это.

## Git

- Папка репозиториев и пути индекса приходят из `python3 <плагин>/scripts/sa_paths.py` (учитывает `SA_REPOS_ROOT`, по умолчанию `~/repos`, и `SA_SYSTEM_DOCS`); папка репозитория — имя сервиса.
- Индекс системы (`bctc.md`, `system_tech.md`) лежит в `index_dir` из вывода `sa_paths.py`.
- `cli`: обычные команды `git -C <repos_root>/<репо> …` (абсолютный путь из `sa_paths.py`), поиск — `grep -rn` или `git grep`.
- Перед чтением кода проверь, что ветка актуальна: отдельными вызовами `git -C <repos_root>/<репо> fetch --quiet`, затем `git -C <repos_root>/<репо> status -sb`. Если локальная ветка отстаёт — скажи пользователю, не делай `pull` сам.
- Не используй переменные окружения в командах Bash — такие команды блокируются; пути бери из `sa_paths.py`.
- Только чтение. Коммиты и пуши в репозитории сервисов — запрещены (кроме `/sa-index-docs`, который пишет в отдельную ветку).

## Ручной режим

- Если аналитик передал путь к локальному файлу (выгрузка BRD или страницы) — прочитай его, это ручной режим.
- Попроси пользователя вставить текст задачи или страницы либо положить выгрузку в `tasks/<KEY>/sources/`.
- Сохрани выжимку в `sources/` с `source: manual` в шапке и пометкой, откуда текст по словам пользователя.

## Запись выбора

После первого успешного обращения запиши режим в `state.json` командой:

```bash
python3 <плагин>/scripts/sa_state.py set tasks/<KEY> access.jira mcp
```

Ключ — `access.jira`, `access.confluence` или `access.git`; получится, например, `"access": {"jira": "mcp", "confluence": "cli", "git": "cli"}`.

Допустимые значения: `mcp`, `cli`, `manual`.
